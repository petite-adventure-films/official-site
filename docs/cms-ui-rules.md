# CMS UI共通ルール

CMSの画面設計・実装・レビュー時に参照する。公開サイトとは別の外観とし、MUIを基盤にする。採用基準はこの文書、具体的な外観・寸法・部品定義はFigmaを正本とする。

## 基準と参照先

編集はPC・1440px・ライトモードを基準にする。文字と余白で整理し、左右の領域は薄い背景と細い境界線で区切る。SPの対応範囲、ダークモード、一覧固有のレイアウトは未決定。

## コンポーネントの境界

- HTML上の意味的な区切りがあり、構造が反復するものを共通コンポーネントにする。
- 共通Layout・Section・Fieldはインスタンスとして使う。名前やAuto Layoutを付けただけのフレームを共通化済みと扱わない。
- 内容はFigmaの標準Slotへ直接配置する。内容の差し替えだけを目的としたSectionContent／FieldContentなどの補助コンポーネントを作らない。
- Sectionは枠で囲まず、見出しと余白で区切る。実装の意味構造は内容に応じてsectionと見出し、fieldsetとlegendなどで表す。
- Fieldはラベルを含めたまとまり。TextFieldだけでなく、Chip群やSwitchも入力・選択要素として扱う。構造と見た目の双方を共通定義へ対応づける。

## 編集画面の配置

- 共通ナビは左。絵文字と項目名を使える。未確定のナビ項目は追加しない。
- ページ上部は一覧へ戻る導線。大きな「○○の編集」見出しは置かず、本文は記事タイトルの入力から始める。
- 本文側に記事内容、右側に管理情報を置く。右側は次のSectionで構成する。
  - 保存・公開：公開状態、保存状態、保存履歴、プレビュー、保存・公開操作、作成日時、最終編集日時。
  - タグ：コンテンツを関連づけるタグ。見出しは「タグ」とする。
  - type固有の設定：イベントの開催状況、対象typeのおすすめなど。画面では具体的な見出しを使う。
- 操作や状態の表示場所をページごとに変更しない。公開操作の詳細や右側の追従動作は別途確定する。

## 入力・選択UI

- 入力幅は基本的に主領域いっぱい。日付など長さが決まるものは、内容に合った幅を使う。
- 一つのFieldは入力要素を1つ以上持てる。複数要素はインラインで並べる。狭い画面の並びはSP設計時に決める。
- 単一選択・複数選択はChip、オン／オフはSwitchを基本とする。Chipに先頭のチェックを付けず、選択状態は共通の外観で示す。SwitchにON/OFFの文字は付けない。
- タグは既存の選択肢をインラインに並べ、選択／解除する。検索UIは付けない。
- フォーム内の開催形式などはField / Outlinedを使い、他の入力欄と枠・ラベル・余白を揃える。右サイドバーのタグなどの枠なしFieldは代表画面の扱いに従う。
- 実装ではラベルとの関連、単一／複数選択・オン／オフの意味、選択状態、キーボード操作を保持する。

## 新しい画面の進め方

1. 対象Issueと依頼範囲を確認し、この文書とFigma共通定義を読む。
2. 各領域を既存Layout・Section・Fieldへ対応づける。内容や状態を定義する前に画面数を増やさない。
3. 相談はページ固有の未決定事項と共通基準の変更が必要な点に絞る。合意済みの基準を毎回問い直さない。
4. まず代表画面を既存の型で組む。状態差分は必要な範囲で確認し、比較用の画面・補助部品を自動的に量産しない。
5. 提出前に以下を実物で確認し、対象の画面仕様にnode・結果・未確認事項を記録する。

提出前確認：

- 外観：基準幅、領域の区切り、余白、ラベル、入力幅、操作の位置、文字切れ・重なり。
- 構造：Layout・Section・Fieldの実際の参照元、標準Slotへの直接配置、参照切れと不要な補助部品の有無。
- 状態：合意した切り替えで必要な入力欄が表示され、内容の保持を含む未確認の動作が明示されていること。
- 提出：静的な外観・構造の確認と、実装での操作・保存・アクセシビリティ確認を区別する。

共通ルールを変更したときは、この文書・Figma定義・対象画面仕様を同じ作業で更新する。本文には現在の結論を記載し、経緯はGitの差分で管理する。
