# PAF Daily Implementation Review

> 目的: PAF移行を進めながら、JS/TS・Astro・React・テスト設計を「説明できる実務スキル」に変える。

---

## 合言葉

- 小さく実装する。
- テストで設計を確かめる。
- 理由を説明する。
- 設計を見直す。
- レビューで直す。
- 事業に接続する。

---

## なぜこの形式でやるのか

PAF移行は、単なるサイト移行ではなく、小さなプロダクトを技術責任者として移行・運用する訓練でもある。

- JS/TSを説明できる
- Astro/Cloudflareで本番運用できる
- Reactで管理画面を作れる
- WordPressから自作CMSへ移行できる
- Stripe/API/Workerの境界を理解できる
- 編集者の業務に接続したCMS設計ができる
- コードレビューで品質を上げられる
- 変更に耐える設計判断ができる
- テストを通じて責務と境界を説明できる

目指すのは「全部知っている人」ではなく、技術を理解し、事業に接続し、人に説明でき、チームが前に進む判断をできる人。

めざせCTO。

## 毎日の流れ

開始条件:

```md
毎朝5時ごろ、このスレッドで「おはよー」と言ったら開始する。
```

Codexは、その日のPAF状況と前回ログを確認し、今日のテーマ候補を1つ提示する。

その後、ユーザーがPre説明と方針説明を行い、Codexが概念フィードバック、方針フィードバック、自力実装・テスト後のコードレビュー、設計レビュー、Postフィードバック、ログ化まで伴走する。

### 1. Pre説明

今日のテーマを、実装前に5分で説明する。

例:

```md
今日のテーマ: wpGetList と Generics

wpGetList<T> の T は、返ってくるデータの型を指定するもの。
たぶん fetch の結果をその型にしてくれる。
```

### 2. Codexの概念フィードバック

Codexが以下を見る。

- 正しい理解
- 誤解している点
- 言葉が曖昧な点
- 今日の実装で確認する観点
- 追加の問い

ここではまだ実装に進まない。

Codexは次の確認をする。

```md
次に、今日どう実装するつもりか方針を出してみて。
```

### 3. 方針説明

ユーザーが、今日の実装方針・設計方針を自分の言葉で説明する。

例:

```md
今日は News 型をAstro側に追加して、wpGetList<News>('news') で一覧を取得する。
ページ側には取得処理を直接書くが、ページネーションの計算は Pager.astro に閉じ込める。
エラー時はまず wpGetList の既存仕様に合わせて空配列にする。
```

### 4. Codex方針フィードバック

Codexはすぐに答えを出さず、まずテスト方針をユーザーに確認する。

```md
先に、何をテストするべきかをあなたの方針で出してみて。
正常系・境界・失敗系のどれを見る？
```

### 5. テスト方針説明

ユーザーが、今日の実装に対して何をテストするかを自分の言葉で説明する。

見る観点:

- 何の責務をテストするか
- どの境界でテストするか
- 正常系・境界値・失敗系のどれを見るか
- 型で守る領域とテストで守る領域をどう分けるか
- そのテストが実装詳細ではなく振る舞いを見ているか

例:

```md
wpGetListはAPI境界なので、URLとqueryの組み立て、fetch成功時、fetch失敗時をテストする。
News型そのものはテストではなくTypeScriptで守る。
newsページ全体は今日は自動テストにせず、buildと目視確認にとどめる。
```

### 6. Codex方針・テスト方針フィードバック

Codexが実装方針とテスト方針をレビューする。

Codexは、いきなり完全な正解を提示しない。まず問い返し、小さなヒント、比較観点を出す。

見る観点:

- 責務の置き場所は自然か
- 型の切り方は適切か
- 実装範囲が大きすぎないか
- 既存PAFコードと一貫しているか
- 将来の変更に弱いところはどこか
- 今日の学習テーマと実装が対応しているか
- 何をテストすべきか
- テストが設計のどの境界を表すか
- 型で守る領域とテストで守る領域が分かれているか
- テストが実装詳細に寄りすぎていないか

Codexはここでもまだ実装しない。

最後に次の確認をする。

```md
方針へのフィードバックはここまで。自力実装に進む？それとも方針をもう少し詰める？
```

ユーザーが明示的に了承したら、PAF実装へ進む。

実装とテストは原則としてユーザーが行う。Codexはコードを書き始めず、実装後のコードレビューとテストレビューを担当する。

ペア実装またはCodex実装は、ユーザーが明示的に依頼した場合だけ行う。

### 7. PAF実装

ユーザーがPAFのコードを1つ進める。小さくてよい。

例:

- `News` 型を追加する
- `/news/` 一覧を作る
- `Pager.astro` を作る
- `wpGetDetail<T>` を追加する
- `PostCard.astro` を拡張する

### 8. テスト実装

ユーザーが、その日の実装に対応するテストを書く。

テストは「壊れていない確認」だけではなく、「この責務はどこにあるか」「この関数・コンポーネントは何を保証するか」を表すものとして書く。

例:

- `Pager` のページ番号生成をテストする
- `wpGetList` のクエリ組み立てをテストする
- イベント一覧の未来イベント抽出ロジックをテストする
- カートの合計金額・送料計算をテストする
- React CMSの入力更新・保存状態をテストする

### 9. Codexコード・テストレビュー

Codexが実装とテストをレビューする。

見る観点:

- 型が適切か
- 関数の責務が分かれているか
- 非同期処理が安全か
- Astro/Reactの流儀に合っているか
- 既存PAFコードと一貫しているか
- エラー時に壊れ方が自然か
- 将来CMS移行しやすいか
- 読んで説明できるコードか
- テストが振る舞いを見ているか
- 実装詳細に依存しすぎていないか
- 正常系・境界値・失敗系のどれを扱ったか
- テスト名から設計意図が読めるか

### 10. Codex設計レビュー

その日の実装を、少し上の視点から見直す。

見る観点:

- この責務はどこに置くべきか
- データの入口と出口はどこか
- ビルド時、ブラウザ、Worker、CMSのどこで処理すべきか
- 変更されやすい部分と安定している部分は何か
- 今は小さく作り、後で拡張できる形になっているか
- 編集者、購入者、運用者にとって自然な構造か
- 障害時にどこを見ればよいか
- 依存先が変わったとき、どこを直せばよいか

問い:

```md
この実装は、将来何が変わったときに壊れやすいか？
```

### 11. 修正

レビューで見つかった点を、その日のうちに直す。

全部直せない場合は、理由と残タスクをログに残す。

### 12. Post説明

同じテーマを、実装後にもう一度5分で説明する。

Pre説明と同じテーマを扱うことで、理解がどう変わったかを見えるようにする。

### 13. CodexのPostフィードバック

Codexが以下を見る。

- Preから改善した点
- まだ曖昧な点
- 実装コードとの対応
- 設計判断として良かった点
- 設計判断としてまだ弱い点
- テストで見えた設計の境界
- 追加で必要なテスト観点
- 次に確認すべき問い
- 明日のテーマ候補

## Codexのコーチング方針

Codexは、すぐに完全な答えを提示しない。

これはテスト方針だけではなく、朝練全体に適用する。

目的は、Codexが正解を配ることではなく、ユーザーが考え、説明し、設計し、実装し、テストし、修正できるようになること。

各フェーズで、まずユーザーに考える余地を渡す。

- 概念: ユーザーが自分の言葉で説明してから、Codexが補正する
- 設計: ユーザーが責務・境界・トレードオフを出してから、Codexがレビューする
- 実装方針: ユーザーが配置場所と理由を出してから、Codexがフィードバックする
- テスト方針: ユーザーが何を守るかを出してから、Codexがレビューする
- レビュー後の修正: Codexがすぐ修正案を書かず、まずユーザーに直し方を考えてもらう
- Post説明: ユーザーが理解の変化を説明してから、Codexが整理する

使う問い:

```md
まずあなたなら何を責務として切る？
その責務はどこでテストするのが自然？
正常系・境界値・失敗系のうち、今日はどれが必要？
それは型で守る領域？テストで守る領域？
そのテストは振る舞いを見ている？実装詳細を見ている？
どこにこのコードを置くのが自然だと思う？
この設計で将来変わりそうなところはどこ？
今の説明で、自分でも少し曖昧だと思う言葉はどれ？
レビュー指摘を直すなら、まずどう変える？
```

ユーザーが答えた後に、Codexがフィードバックする。

フィードバックの順番:

1. すでに良いところ
2. 考えを鋭くする問い
3. 小さな補正・ヒント
4. 必要な場合だけ具体案

Codexが完全な案を出すのは、ユーザーが求めたとき、詰まったとき、またはユーザーが一度考えを出した後に限る。

具体案を出す場合も「唯一の正解」ではなく、「一つの案」として提示する。
