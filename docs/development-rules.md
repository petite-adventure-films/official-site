# 開発・実装ルール

公開サイト・SHOP・CMS・デザインシステム・移行処理・運用に共通して適用する。

## 正本と役割

- 原則は `.specify/memory/constitution.md`、品質条件は `docs/quality-criteria.md` を正本とする。
- 作業の目的・範囲・受け入れ条件はGitHub Issue、予定と優先順位はGitHub Projectsで管理する。
- Spec Kitの `specs/` は仕様・設計・タスクとその確認資料をGit管理する。検討中・合意済みなどの状態を明示し、実装とともに更新する。
- `docs/` は現在の運用・共通ルールを簡潔に記載し、機能仕様は `specs/` を参照する。Issueには目的・範囲・受け入れ条件の要点と仕様への参照を置く。
- 変更の経緯はGitの差分・コミット・PRでたどる。文書本文は現在の内容へ更新し、同じ内容を複数箇所で保守しない。

## 進め方

- Issueの目的・範囲・受け入れ条件を確認し、未確定事項は明示する。結果を左右する曖昧さを推測で確定しない。
- 要件、設計、作業分解を区別し、原則・品質基準・仕様との整合性を確認する。Spec Kitの生成結果は確認してから次の段階へ進める。
- 計画・仕様・画面設計の依頼を、実装開始の承認と扱わない。実装は合意した範囲で行う。
- UIは共通デザインシステムに沿って設計・実装・確認する。部品や基準の追加・変更は、その正本にも反映する。
- 小さな修正は目的・変更範囲・確認方法をIssueまたはPRに記載し、変更規模に応じて資料を絞る。

## ブランチ運用

- ファイルを変更する前に、対象Issue、現在のブランチ、未コミット変更、関連PRの状態、リモートの最新状態を確認する。
- 分岐元とPRのマージ先は、対象作業の統合先とCI・デプロイ設定に基づいて決める。GitHubのデフォルトブランチと開発の統合先を区別する。
- 仕様・設計の編集から作業単位のブランチを使う。既存ブランチを継続する場合は、同じ作業範囲であり、関連PRが未マージであることを確認する。
- マージ済みの作業から新しい変更を始める場合は、統合先の最新状態から新規ブランチを作る。ブランチ名は目的が分かる名前とし、機能作業ではIssue番号を含める。
- 未コミット変更は内容と所属する作業を確認して保持し、別作業を混在させない。必要に応じて別worktreeを使う。
- 作業開始時に、使用するブランチ・分岐元・PRのマージ先を共有する。

## デザインシステムの管理

- トークン・コンポーネント・レイアウトの設計はFigmaを正本とする。
- スタイリングにはTailwind CSSを使用する。Figma由来のトークンをTailwindのテーマへ対応させ、ユーティリティから参照する。通常のCSSが必要な状態指定などでも同じトークンを使う。
- 部品固有のFigma参照先は、対応するコンポーネントの先頭コメントにnode-id付きURLで記録する。トークンは `astro/src/styles/tokens.css` に置き、参照先も同ファイルに記録する。
- 変更時は参照URLからMCPで定義・変数を読み、トークンと対応するコードへ反映する。通常の `npm run dev` で実際の利用画面を確認し、共有部品は他の利用画面への影響も確認する。
- UIは、デザインシステムで定義したコンポーネントまたは共通スタイルを通じて実装する。色・文字・余白などの値はトークンを参照し、必要な定義がなければデザインシステムに追加する。
- コードでは設計に対応する実装とテストを管理する。Gitの文書では選択基準・更新ルールを管理し、Figmaの定義を重複して保守しない。
- 操作と対象端末での表示は、実際の画面とテストで確認する。公開サイトのアクセシビリティは共通品質基準に従って確認する。Figma上の確認だけで実装の品質を判断しない。

### 画面設計の開始・完了条件

- CMSは [CMS UI共通ルール](cms-ui-rules.md) を開始条件・提出前確認に使う。合意済みの基準を引き継ぎ、新しい画面では固有の未決定事項だけを相談する。
- 依頼への着手許可と、未決定の仕様を確定する許可を区別する。既存の基準に適用できない点は提案として示し、合意後に反映する。
- 着手前に、必要な部品・画面パターンをFigmaの定義へ対応づけ、参照nodeと確認状況を対象仕様に記録する。色・文字・余白の定義だけで、画面を構成する準備が整ったとは判断しない。
- 必要な定義が不足する場合は、共通部品と代表画面で型を整える。利用者がその型を確認してから他画面へ展開する。AIによる作成・検査と、利用者による確認を区別する。
- 画面の表示・操作要素は、定義したコンポーネントのインスタンスで構成する。テキスト・図形はコンポーネント内部で定義し、画面上での直接配置は配置用コンテナと設計注記に限る。共通スタイルの適用だけでコンポーネント化済みと扱わない。
- 提出前にレイヤー構造を検査し、各インスタンスの参照元、インスタンス外の表示・操作要素、トークンとの対応を確認する。対象nodeと検査結果を対象仕様に残す。スクリーンショットの確認と構造の確認を両方行い、不適合が残る案は修正対象と明示して、他画面への展開・実装の基準に使わない。

## Spec Kit

- Spec Kit 1.3.2のCodex用スキルとshスクリプトを使用する。設定は `.specify/`、スキルは `.agents/skills/` に配置する。
- 要件整理は `$speckit-specify`、曖昧さの確認は `$speckit-clarify`、設計は `$speckit-plan`、作業分解は `$speckit-tasks`、整合性確認は `$speckit-analyze` を使う。各段階の結果を確認して進む。
- `$speckit-implement` と `$speckit-converge` は実装作業の合意後に使用する。convergeの判定だけで完了とはしない。
- 原則を変更する必要があるときだけ `$speckit-constitution` を使う。標準テンプレートの指定より本プロジェクトの合意を優先し、原則本文に運用説明・変更履歴・バージョン情報を追加しない。
- 生成する仕様には対象Issueを明記する。仕様フォルダの番号とIssue番号は別物とし、Gitのブランチは作業単位で管理する。Git拡張は導入しない。
- 標準スキルやテンプレートを更新するときも、原則の保持・文書の管理対象・段階ごとの合意・テストの実施判断を確認する。生成手順の推奨だけでこれらを変更しない。

## 実装と確認

- UI変更は開発中にローカルで表示・操作を確認する。重要な利用経路のPlaywrightテストを維持する。
- CMSの主要機能と公開経路が一巡するまで、PRとpush前のPlaywright自動実行を休止する。必要なときはリポジトリ直下から公開サイトを `pnpm --dir astro run test:e2e`、CMSを `pnpm --dir cms run test:e2e` で確認する。
- 本番切り替え前に、保存・再編集・公開・既存URLへのアクセスを通しで確認する。主要機能と公開経路が揃った段階で、`scripts/e2e-scope.mjs` の変更範囲判定を使い、PRとpush前の自動実行を再開する。
- PlaywrightのHTMLレポートと失敗時のスクリーンショット・トレースをCIの成果物として保存する。自動検査・手動確認の結果と未確認事項をPR本文に記載する。
- 変更する振る舞いと影響範囲に応じて、必要なテストを追加・実行する。具体的な方法は各実装で決める。
- 自動テストでは確認できない点は手動で確認し、結果と未確認事項をPRなどのレビュー対象に示す。
- テストの成功だけで品質基準を満たしたと判断しない。未確認事項が受け入れ条件に関わる場合は、完了扱いにしない。
- 変更後は実装と採用済みの仕様・設計・運用文書を一致させる。
