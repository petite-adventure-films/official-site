# 開発・実装ルール

公開サイト・SHOP・CMS・デザインシステム・移行処理・運用に共通して適用する。

## 正本と役割

- 原則は `.specify/memory/constitution.md`、品質条件は `docs/quality-criteria.md` を正本とする。
- 作業の目的・範囲・受け入れ条件はGitHub Issue、予定と優先順位はGitHub Projectsで管理する。
- Spec Kitの `specs/` は仕様の整理・設計・作業分解に使うローカル作業領域とする。計画・タスク・検討経緯を自動的にGitへ追加しない。
- 採用した仕様・設計・運用上の結論は、実装とともに参照できる文書へ反映する。既存の正本を更新し、同じ内容を複数箇所で保守しない。

## 進め方

- Issueの目的・範囲・受け入れ条件を確認し、未確定事項は明示する。結果を左右する曖昧さを推測で確定しない。
- 要件、設計、作業分解を区別し、原則・品質基準・仕様との整合性を確認する。Spec Kitの生成結果は確認してから次の段階へ進める。
- 計画・仕様・画面設計の依頼を、実装開始の承認と扱わない。実装は合意した範囲で行う。
- UIは共通デザインシステムに沿って設計・実装・確認する。部品や基準の追加・変更は、その正本にも反映する。
- 小さな修正は目的・変更範囲・確認方法をIssueまたはPRに記載し、変更規模に応じて資料を絞る。

## デザインシステムの管理

- トークン・コンポーネント・レイアウトの設計はFigmaを正本とする。
- コードでは設計に対応する実装とテストを管理する。Gitの文書では選択基準・更新ルールを管理し、Figmaの定義を重複して保守しない。
- 操作・レスポンシブ表示・アクセシビリティは、実際の画面とテストで確認する。Figma上の確認だけで実装の品質を判断しない。
- Storybookは現時点では導入しない。実際の画面だけでは部品の状態を確認しづらくなった場合に、補助ツールの必要性を再検討する。

## Spec Kit

- Spec Kit 1.3.2のCodex用スキルとshスクリプトを使用する。設定は `.specify/`、スキルは `.agents/skills/` に配置する。
- 要件整理は `$speckit-specify`、曖昧さの確認は `$speckit-clarify`、設計は `$speckit-plan`、作業分解は `$speckit-tasks`、整合性確認は `$speckit-analyze` を使う。各段階の結果を確認して進む。
- `$speckit-implement` と `$speckit-converge` は実装作業の合意後に使用する。convergeの判定だけで完了とはしない。
- 原則を変更する必要があるときだけ `$speckit-constitution` を使う。標準テンプレートの指定より本プロジェクトの合意を優先し、原則本文に運用説明・変更履歴・バージョン情報を追加しない。
- 生成する仕様には対象Issueを明記する。仕様フォルダの番号とIssue番号は別物とし、Gitのブランチは作業単位で管理する。Git拡張は導入しない。
- 標準スキルやテンプレートを更新するときも、原則の保持・文書の管理対象・段階ごとの合意・テストの実施判断を確認する。生成手順の推奨だけでこれらを変更しない。

## 実装と確認

- 変更する振る舞いと影響範囲に応じて、必要なテストを追加・実行する。具体的な方法は各実装で決める。
- 自動テストでは確認できない点は手動で確認し、結果と未確認事項をPRなどのレビュー対象に示す。
- テストの成功だけで品質基準を満たしたと判断しない。未確認事項が受け入れ条件に関わる場合は、完了扱いにしない。
- 変更後は実装と採用済みの仕様・設計・運用文書を一致させる。
