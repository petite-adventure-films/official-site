# 2026-06-10: published型とテスト判断基準

## テーマ

WordPress API から返る `published` を、API response 型として扱うか、画面表示用の型として扱うかを判断する。

あわせて、今回の変更で自動テストを書くべきか、型チェック・ビルド確認で十分かを判断する。

## Pre説明

まず、API から返ってくるデータの型がどうなのか、使う場面がどうなっているかを見る。

そのうえで型定義し、必要なら整形する。

整形は他にも使えそうなら util 化や日付表示用コンポーネント化を考えるが、まだ共通化してよいか判断材料が少ないため、今日は念頭に置くくらいにする。

## Codex Preフィードバック

API から返る型と画面で使う型を先に分けて考える順番はよい。

`News` を API response 型として置くなら、`published` は WordPress API が返す値を表すべき。

今回の WordPress 側実装では `published` に `get_the_date()` を入れている。公式の返り値は `string|int|false` だが、このPAF実装では無引数で表示用日付文字列として使っており、既存 Vue 側の `News` 型や他の API 型も `published: string` として扱っている。

したがって、Astro 側の `News.published` も `string` に寄せるのが自然。

ただし、API 境界で実行時検証をしているわけではないため、将来自作 CMS に移行する場合は、API response 型、画面表示用型、正規化処理の境界を改めて設計する必要がある。

## 方針説明

`News` 型は、API から返ってくるそのままの型として定義する。

整形の責務は受け取り側、つまり表示側にあると考える。

ただし今回は、そもそも WordPress 側の `get_the_date()` によって表示用日付として整形済みの値が渡ってきているため、フロント側ではそのまま受け取る。

自作 CMS になったときは、CMS 側で機械的な日付を返すか、フロント側で表示用に整形するかを設計する。

## テスト方針

今回の変更は、`published` を実データに合わせて `string` として扱う型判断が中心。

フロント側で日付整形関数や正規化関数を追加しないため、自動テストの対象になる自前ロジックはまだない。

WordPress から実際にどんな日付文字列が返るかを見るのは、テストではなく調査・デバッグ。

今回は自動テストを追加せず、型チェックとビルドで確認する判断にする。

## Codex 方針・テスト方針フィードバック

`News.published` を `string` にする判断は、API 実装と既存型に合っている。

表示用テキストとしては `post.published` をそのまま使えるが、`<time datetime="">` に表示用文字列を入れてよいかは別問題。

`datetime` には本来 `2026-06-10` のような機械可読な値が望ましいため、将来的には `published` と `publishedDateTime`、または `publishedAt` と `publishedLabel` を分ける余地がある。

今回、自前の変換ロジックを追加しないなら、日付整形関数のテストは不要。

テストは関数の有無ではなく、壊れたら困る判断をチームの資産として残すために書く。

API が変わるとき、型定義を返ってくるものに合わせるか、表示する側に合わせるかを判断する必要がある。

今回、自分の場合は `News` を API から返るデータとして持つ。

整形の責務は表示側にある。

テストの基準は、壊れたら困る判断を、チームの資産として残すもの。

## Codex Postフィードバック

API response 型と画面表示用型のどちらを定義しているのか、という問いを持てたのがよい。

今回は WordPress 側がすでに表示用日付文字列を返しているため、Astro 側の `News.published` は `string` として持つ。

一方で、将来自作 CMS に移るときは、API が機械可読な日付を返し、画面側で表示用に整形する設計の方が変更に強い可能性がある。

テストについては、API レスポンスの実態確認と、自前ロジックの仕様保証を分けて考えられた。
