# 2026-06-11: news一覧ページャー設計

## テーマ

`news` 一覧にページャーを追加する前に、データ取得、URL、ページコンポーネント、`Pager`、テスト境界の責務を整理する。

## Pre説明

`News` は一覧を表示するための1件分のデータ型として考える。詳細ページ用のデータまではまだ含めない。

`wpGetList` は API 通信の境界。エラーを考えるなら、API から返るエラーをどう扱うかを見る。

`Pager` はページ送りを表示する責務を持つ。

## Codex Preフィードバック

`News` にページャー情報を混ぜない考え方は自然。

`News` は一覧の1件分のデータ型で、`total_pages` は一覧レスポンス全体のメタ情報として扱う。

ページコンポーネントは、URL から現在ページを判断し、データを取得し、取得結果を表示部品に渡してページ全体を組み立てる責務を持つ。

`Pager` は `currentPage`, `totalPages`, `basePath` などを受け取り、ページ移動 UI を表示する責務を持つ。

## 方針説明

`/news/page/1` のような URL を考えた。

最初は `wpGetList` に渡すものはないと考えたが、ページごとに通信する場合は、`page` と `per_page` をクエリとして渡す必要がある。

全件取得して Astro 側で分割する方法と、ページごとに API 通信する方法を比較した。

件数だけではなく、通信速度、API 仕様、サーバー負荷、キャッシュ、更新頻度、ユーザー体験によって判断する必要がある。

今回の `news` 一覧では、`wpGetList` がすでに `total_pages` を返しているため、ページごと取得で進める方針が自然。

## テスト方針

表示そのものより、ページ番号をどう返すかをテスト対象にする。

`buildPageItems(currentPage, totalPages)` のような純粋関数を作るなら、そこに対してテストを書く。

見るケース:

- 正常系: 現在ページの前後に期待するページ番号が出る
- 境界: `currentPage = 1` のとき前ページが出ない、または disabled になる
- 境界: `currentPage = totalPages` のとき次ページが出ない、または disabled になる
- 境界: `totalPages = 1` のときページャーを表示しない判断ができる
- 失敗系: `currentPage` が範囲外のときどう扱うか

範囲外ページは、最新ページへリダイレクトするのではなく 404 として扱う方針にした。

## Codex 方針・テスト方針フィードバック

ページャーは UI だけではなく、データ取得戦略、URL 設計、404 判断、テスト境界までつながる設計対象。

`buildPageItems` は有効な `currentPage` / `totalPages` を受け取り、表示するページ番号を返す。

範囲外ページの判定は、`Pager` や `buildPageItems` ではなく、ページコンポーネント側で URL と `total_pages` を見て 404 にするのが自然。

`wpGetList` は API から `{ data, total_pages }` を返し、API エラー時は既存仕様どおり `{ data: [], total_pages: 0 }` を返す。
