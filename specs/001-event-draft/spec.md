**対象Issue**: https://github.com/petite-adventure-films/official-site/issues/392

Issue本文と現行の原則・品質基準・開発ルールを根拠とする。過去のローカル試行案は採用済みの根拠にしない。合意済み事項と残る提案を区別する。今回は利用者が下記3段階の実装着手を承認済み。未決定の公開・削除ルールは推測で確定しない。

## CMS共通機能との関係

認証・新規作成・保存・複製・履歴・復元・プレビュー切替は [CMS共通設計](../002-cms-foundation/spec.md) に従う。この仕様ではイベントを最初の利用例として受け入れ条件を定義し、開催情報・タグ・表示内容を具体化する。

## 合意した対象と確認順序

詳細ページのプレビュー、連続期間の開催、オンライン開催、告知の複製を #392 の必須範囲に含める。シリーズの各回は別々の告知として登録し、シリーズ名はタイトルや説明に記載する。仕様とFigma画面設計では最初から全範囲を扱う。

確認順序は、単日・会場開催の作成→保存→再編集、詳細プレビュー、複数日・オンライン開催とする。これは実装と検証の分割であり、後続機能への先送りではない。最初の段階だけでは #392 を完了としない。

日程の正本はGitHub Projectsとする。全範囲を現在の保存・再編集の予定枠に含める想定だが、設計で成立性を確認し、必要なら必須範囲を維持して予定を見直す。

## 実装と確認の進め方

今回の対象は、①編集・保存・再編集・複製・プレビュー、②公開・公開停止・公開履歴・履歴復元、③ゴミ箱への移動・復元・30日後の完全削除。①→②→③の順に実装・テストする。①だけで今回の対象全体を完了としない。実行タスクの正本は [tasks.md](tasks.md)。

テストは開発側で進め、利用者のPCでの操作確認は後日行う。本人の操作確認待ちだけでは実装を止めず、未実施として記録する。仕様判断が必要なら利用者へ確認できる。自動テストだけで手動確認やWCAG全体を確認済みとは扱わない。

## User Scenarios & Testing

### User Story 1 - 新しい告知を保存し、編集を再開する (Priority: P1)

監督が空の状態からイベント告知を作成し、途中で下書きを保存して、後から続きを入力できる。

**Why this priority**: WordPressに代わる告知作成の最初の業務を成立させる。
**Independent Test**: 新規作成、入力、保存、画面を離れて再表示、修正、再保存を一巡する。

**Acceptance Scenarios**:
1. **Given** 作成権限がある、**When** 新規作成を始める、**Then** 他の告知の内容が混入しない空の告知を入力できる。
2. **Given** 告知を入力した、**When** 下書き保存が成功して開き直す、**Then** 保存した各項目が保持され、続きから編集できる。
3. **Given** 映画タグ・イベントタグが未選択、**When** 保存する、**Then** タグ選択を要求せず保存できる。各タグを複数選択した場合も保持する。
4. **Given** 告知を保存した、**When** 公開サイトと権限のない利用者から確認する、**Then** 下書きは取得できず、既存の公開内容も変わらない。

### User Story 2 - 保存状態を理解して失敗から回復する (Priority: P1)

監督が保存済みかどうかを把握し、保存失敗時も入力を保って再試行できる。

**Why this priority**: 保存したつもりで入力を失うことを防ぐ。
**Independent Test**: 保存処理の遅延・失敗・再試行を再現する。

**Acceptance Scenarios**:
1. **Given** 編集中、**When** 保存が開始・成功・失敗する、**Then** 未保存・保存中・保存済み・保存失敗を区別できる。
2. **Given** 保存に失敗した、**When** 同じ画面で操作を続ける、**Then** 入力は残り、失敗を認識して再試行できる。
3. **Given** 保存処理中に追加入力した、**When** 前の保存が完了する、**Then** 追加入力まで保存されたと誤表示しない。

### User Story 3 - 詳細表示を確認する (Priority: P1)

監督が公開前にイベントの詳細表示を確認できる。

**Why this priority**: 告知の内容と見え方を確認する必須操作である。
**Independent Test**: 保存済みの告知に未保存の変更を加えてプレビューし、現在の入力情報と照合する。

**Acceptance Scenarios**:
1. **Given** 作成した告知、**When** 詳細プレビューを開く、**Then** 未保存分を含め、プレビューを開いた時点の入力内容を確認できる。プレビュー操作で公開されない。
2. **Given** 下書きのプレビュー、**When** 権限のない利用者がアクセスする、**Then** 内容を取得できない。

3. **Given** 未保存の変更がある、**When** プレビューを開く、**Then** 保存済みの古い内容に置き換わらず、保存状態は実際の保存結果に従って別に表示される。

### User Story 4 - 連続期間・オンライン開催を告知する (Priority: P1)

監督が連続期間の開催とオンライン開催の告知を作成し、保存・再編集・詳細プレビューできる。

**Why this priority**: いずれも今回の必須の開催形式である。
**Independent Test**: 年をまたぐ連続期間とオンライン開催の代表例それぞれで全操作を一巡する。

**Acceptance Scenarios**:
1. **Given** 連続期間の告知、**When** 保存して再編集・プレビューする、**Then** 年を含む開始日・終了日が保持される。
2. **Given** オンライン開催の告知、**When** 保存して再編集・プレビューする、**Then** オンラインの開催案内が保持され、架空の会場や住所を入力させない。

開催形式はオフライン／オンラインを複数選択でき、併催を扱う。参加方法・URLは開催場所の備考へ入力する。非公開の接続情報を保存する専用項目は設けない。入力欄は [画面契約](contracts/screens.md) に従う。

### User Story 5 - 告知を複製して次の回を作成する (Priority: P1)

監督が既存の告知を複製し、日時・会場などを変更して別の告知を作成できる。

**Why this priority**: シリーズの各回を独立して扱いながら、共通情報の再入力を省く。
**Independent Test**: 告知を複製して別日・別会場へ変更し、保存・再編集・プレビューする。

**Acceptance Scenarios**:
1. **Given** 既存の告知、**When** 複製する、**Then** 内容を引き継いだ別の告知の下書きが作成され、公開されない。
2. **Given** 複製した下書き、**When** 日時・会場を変更して保存する、**Then** 元の告知は変更されず、それぞれの内容を再編集・プレビューできる。
3. **Given** シリーズの各回を別々に登録している、**When** 一方を延期・中止にする、**Then** その告知だけに開催状態が適用される。

複製はCMS共通の操作とし、日時・開催状態を含む入力内容をそのままコピーする。今回の対応種別はイベント。新しい告知は独立した下書きとし、識別子・公開状態・公開履歴は新規として扱う。

### User Story 6 - 公開して履歴から戻す (Priority: P1)

監督が内容を確認して公開・公開停止し、公開した内容を履歴から下書きへ戻せる。

**Independent Test**: テスト環境で公開成功・失敗・再送と公開停止を再現し、公開内容と履歴が一致することを確認する。公開履歴から復元しても再公開されず、復元前の下書きへ戻し直せる。
**Acceptance Scenarios**: 公開検証に失敗したら公開内容を変更しない。成功時だけ公開履歴を作り、直近3件・期限なしで保持する。反復復元は直前の下書き1件を入れ替え、失敗・競合・再送で保護内容を失わない。公開成功の定義と配信への接続は段階②の先頭で設計する。

### User Story 7 - ゴミ箱から復元する (Priority: P1)

監督が記事をゴミ箱へ移し、30日以内なら下書きとして戻せる。

**Independent Test**: テスト環境で公開記事・下書きをゴミ箱へ移し、復元・期限境界・定期処理の再実行を確認する。
**Acceptance Scenarios**: ゴミ箱への移動は確認を経て実行し、公開中なら公開を停止する。復元では再公開せず、ゴミ箱の一覧に留まる。移動後30日を経過した記事は自動で完全削除する。期限・失敗・関連データ削除・復元との競合の契約は段階③の先頭で具体化する。

### 公開イベント一覧との整合条件

開催日程の保存・表示を設計する際は、次の公開一覧の方針に合わせる。公開一覧の実装変更は #394 との担当範囲を設計時に整理する。

- 最新一覧には今日以降に開催する告知を掲載し、開催日が近い順に並べる。連続開催中の告知も終了日までは掲載対象とし、その並び順は詳細設計で定義する。告知の開始年を掲載条件にしない。
- 月別一覧はタブで切り替える。各告知の開催日・期間で年月に分類し、異なる年の同じ月を区別する。
- 年をまたぐシリーズは各回を別の告知として扱う。12月20日と翌年1月10日の告知がある場合、年明けは1月10日の告知が最新一覧に残る。
- 飛び日の間に開催日を補わない。月別一覧では実際に開催する月に掲載する。

確認例: 12月20日・翌年1月10日の別々の告知と翌年1月5日の告知がある場合、1月1日の最新一覧は1月5日、1月10日の順になる。12月・翌年1月のタブで該当する開催情報を確認する。

### Edge Cases

- タイトル・開催日・会場などが空欄でも下書き保存できる。自動保存・保存ボタンとも同じ条件とし、公開時の必須条件と分ける。
- 入力途中・不成立の日付・終了日逆転も、入力した内容のまま下書きに保存し、再表示できる。問題箇所の表示と保存の成否を分ける。プレビューでは勝手に補正せず、公開時は検証して不正な内容の公開を止める。保存可能なデータ形式・容量の制限に抵触した場合は保存失敗を明示し、画面の入力を保持する。
- 権限失効時は保存成功と表示しない。再認証の導線と入力保持の方法は設計で確認する。
- 複数画面から編集した際に黙って上書きしない。保存世代の照合・409応答・入力保持はCMS共通設計に従う。
- ブラウザー終了後はサーバーへの保存が成功した内容まで復旧を保証する。未保存の変更がある間は離脱時に警告する。強制終了などで失われた未保存入力の復旧は今回の保証に含めず、端末内への復旧用バックアップは設けない。

## Requirements

### Functional Requirements

- **FR-001**: 権限を持つ利用者が空からイベント告知を作成できる。
- **FR-002**: 入力内容を下書き保存し、同じ告知を再度開いて編集できる。
- **FR-003**: 映画タグ・イベントタグはそれぞれ任意・複数選択とする。
- **FR-004**: 下書き保存では公開せず、下書きの閲覧・変更にアクセス制御を適用する。認証は今回の必須範囲とし、管理画面と保存・取得・プレビューの各処理で未認証・未許可のアクセスを拒否する。
- **FR-005**: 未保存・保存中・保存済み・失敗を利用者が区別できる。失敗を成功扱いしない。
- **FR-006**: 保存失敗時は同じ画面で入力を保持し、再試行できる。
- **FR-007**: 入力・選択変更が止まって1秒後に自動保存する。保存ボタンも併用し、押した場合は待たずに保存する。どちらも最新の下書きだけを保存し、公開履歴は作成しない。
- **FR-008**: 共通品質基準に従い、全操作をキーボードで行え、ラベル・保存状態・エラーが認識できることを含めて評価する。
- **FR-009**: 単日・会場開催、複数日開催、オンライン開催の作成・下書き保存・再編集を必須範囲とする。連続期間は1件の告知で開始日・終了日を扱う。離れた日程や時間・会場が異なるシリーズの各回は別々の告知として登録する。
- **FR-009b**: 開催形式は下書きでは全解除でき、未選択のまま保存・再編集できる。公開時はオフライン／オンラインの少なくとも1つの選択を必須とする。
- **FR-009a**: 複数日・開催形式の切り替えで非表示になった入力も下書きに保持する。設定を戻すと再表示し、保存・再編集をまたいでも保持する。非表示項目はプレビュー・公開の対象から除外する。
- **FR-010**: 各開催形式で、未保存分を含むプレビュー表示時点の入力内容を非公開の詳細ページプレビューで確認できる。保存状態は別に表示し、プレビューの表示成功を保存成功として扱わない。プレビューでは公開を実行しない。

- **FR-011**: 既存の告知を複製して新しい下書きを作成できる。複製後は独立して日時・会場などを変更でき、元の告知に影響しない。
- **FR-012**: 延期・中止は告知単位で設定・表示できる。

- **FR-013**: 公開履歴から過去の内容を確認し、同じ告知の新しい下書き版として復元できる機能を今回に含める方針。履歴の作成契機と保持方針はCMS共通設計に従い、復元前保護の操作・反復復元時の扱いもCMS共通設計に従う。段階②で公開処理と接続して実装する。復元では公開せず、復元前の保存内容も保持する。

- **FR-014**: 確認操作と公開用の検証を経て公開・公開停止でき、公開成功と履歴生成の整合性を保つ。
- **FR-015**: ゴミ箱へ移動した記事を30日以内に下書きとして復元でき、移動後30日を経過したら自動で完全削除する。

### Key Entities

- **イベント下書き**: 告知の識別、入力内容、保存状態、作成者のアクセス権。開催日程は単日または連続期間を扱う。告知ごとに日時・会場・開催状態を持つ。入力項目は [画面契約](contracts/screens.md#本文の入力) を正本とし、保存データは [データ設計](data-model.md) に対応づける。空欄・不正値も下書き保存する。文字数・容量上限の具体値は設計で確定する。
- **映画タグ／イベントタグ**: 告知に関連づける分類。どちらも任意で複数選択できる。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 合意した代表例で作成→保存→再表示→修正→再保存を完遂し、保存対象の全項目が一致する。
- **SC-002**: タグ未選択・複数選択の両方で保存と再編集を完遂する。
- **SC-003**: 保存失敗を再現して、入力保持・失敗表示・再試行成功の3点を確認する。
- **SC-004**: 権限のない利用者が下書きを取得・変更できないこと、保存で公開内容が変わらないことを確認する。
- **SC-005**: WCAG 2.2 A・AAの達成基準ごとに結果と根拠を記録し、未確認を適合としない。監督の操作確認と開発担当者の検証を分けて記録する。

- **SC-006**: 単日・会場開催、連続期間、複製して作成した別日程の告知、オンライン開催の代表例すべてで、作成・保存・再編集・詳細プレビューを確認する。いずれか未確認なら本Issueを完了としない。

- **SC-007**: 複製による新規下書きの作成・変更・保存・再編集・プレビューを確認し、元の告知が変わらないこと、複製した告知が公開されないことを確認する。

## Assumptions

- 管理画面の利用者は監督と開発担当者の2人。個別アカウント・同じ操作権限で開始する。利用許可・解除の方法、ログイン・ログアウト・セッション期限切れ・復旧を認証設計で具体化する。開発担当者専用の操作が必要になった時点で、その操作の制限を設計する。認証・保存構成はCMS共通設計のCloudflare Accessメールコード・専用Worker・D1で確認済み。導入設定と復旧方法は未確定。
- 一覧・検索・ページ送りは画面設計の対象。検索の詳細と実装範囲は [画面契約](contracts/screens.md#イベント一覧) と [残る確認事項](../002-cms-foundation/plan.md#残る確認事項) に従う。
- 他のコンテンツ種別、公開待ち、移行、アップロード、決済は本仕様の範囲外。公開・公開停止・ゴミ箱は今回の3段階に含む。
- 共通デザインシステムの既存画面を基準に、未作成の状態を補いながら3段階で実装する。
- #397（保存）、#396（スキーマ）、#334（本文編集）との境界は設計段階で照合する。
