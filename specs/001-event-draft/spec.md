## 合意した対象と確認順序

詳細ページのプレビュー、複数日開催、オンライン開催を #392 の必須範囲に含める。仕様とFigma画面設計では最初から全範囲を扱う。

確認順序は、単日・会場開催の作成→保存→再編集、詳細プレビュー、複数日・オンライン開催とする。これは実装と検証の分割であり、後続機能への先送りではない。最初の段階だけでは #392 を完了としない。

日程の正本はGitHub Projectsとする。全範囲を現在の保存・再編集の予定枠に含める想定だが、設計で成立性を確認し、必要なら必須範囲を維持して予定を見直す。

## User Scenarios & Testing

### User Story 1 - 新しい告知を保存し、編集を再開する (Priority: P1)

監督が空の状態からイベント告知を作成し、途中で下書きを保存して、後から続きを入力できる。

**Why this priority**: WordPressに代わる告知作成の最初の業務を成立させる。
**Independent Test**: 新規作成、入力、保存、画面を離れて再表示、修正、再保存を一巡する。

**Acceptance Scenarios**:
1. **Given** 作成権限がある、**When** 新規作成を始める、**Then** 他の告知の内容が混入しない空の告知を入力できる。
2. **Given** 告知を入力した、**When** 下書き保存が成功して開き直す、**Then** 保存した各項目が保持され、続きから編集できる。
3. **Given** 映画タグ・イベントタグが未選択、**When** 保存する、**Then** タグ選択を要求せず保存できる。各タグを複数選択した場合も保持する。
4. **Given** 告知を保存した、**When** 公開サイトと権限のない利用者から確認する、**Then** 下書きは取得できず、既存の公開内容も変わらない。

### User Story 2 - 保存状態を理解して失敗から回復する (Priority: P1)

監督が保存済みかどうかを把握し、保存失敗時も入力を保って再試行できる。

**Why this priority**: 保存したつもりで入力を失うことを防ぐ。
**Independent Test**: 保存処理の遅延・失敗・再試行を再現する。

**Acceptance Scenarios**:
1. **Given** 編集中、**When** 保存が開始・成功・失敗する、**Then** 未保存・保存中・保存済み・保存失敗を区別できる。
2. **Given** 保存に失敗した、**When** 同じ画面で操作を続ける、**Then** 入力は残り、失敗を認識して再試行できる。
3. **Given** 保存処理中に追加入力した、**When** 前の保存が完了する、**Then** 追加入力まで保存されたと誤表示しない。

### User Story 3 - 詳細表示を確認する (Priority: P1)

監督が公開前にイベントの詳細表示を確認できる。

**Why this priority**: 告知の内容と見え方を確認する必須操作である。
**Independent Test**: 対象の告知をプレビューし、入力情報と照合する。

**Acceptance Scenarios**:
1. **Given** 作成した告知、**When** 詳細プレビューを開く、**Then** 対象の告知の内容を確認でき、プレビュー操作で公開されない。
2. **Given** 下書きのプレビュー、**When** 権限のない利用者がアクセスする、**Then** 内容を取得できない。

プレビューが保存済み内容か未保存の入力を表示するかは未確定。表示対象と保存への影響を詳細仕様で明示する。

### User Story 4 - 複数日・オンライン開催を告知する (Priority: P1)

監督が複数日開催とオンライン開催の告知を作成し、保存・再編集・詳細プレビューできる。

**Why this priority**: いずれも今回の必須の開催形式である。
**Independent Test**: 複数日開催とオンライン開催の代表例それぞれで全操作を一巡する。

**Acceptance Scenarios**:
1. **Given** 複数日開催の告知、**When** 保存して再編集・プレビューする、**Then** 開催日程が保持され、単日へ勝手に変換されない。
2. **Given** オンライン開催の告知、**When** 保存して再編集・プレビューする、**Then** オンラインの開催案内が保持され、架空の会場や住所を入力させない。

連続期間と飛び日の表現、参加案内と非公開の接続情報の区別、会場とオンラインの併催は詳細仕様で確認する。

### Edge Cases

- タイトルや開催日が未入力の途中状態も保存可能とする提案。公開時の必須条件と分ける。Issue本文では明文化されていないため、レビュー対象とする。
- 不正な日付は勝手に補正・消去せず、入力内容と問題箇所を示す提案。不正値の永続保存の可否は設計前に決める。
- 権限失効時は保存成功と表示しない。再認証の導線と入力保持の方法は設計で確認する。
- 複数画面から編集した際に黙って上書きしない提案。競合への対応は保存設計で具体化する。
- ブラウザ終了後の未保存データ復元は今回の保証に含めない提案。

## Requirements

### Functional Requirements

- **FR-001**: 権限を持つ利用者が空からイベント告知を作成できる。
- **FR-002**: 入力内容を下書き保存し、同じ告知を再度開いて編集できる。
- **FR-003**: 映画タグ・イベントタグはそれぞれ任意・複数選択とする。
- **FR-004**: 下書き保存では公開せず、下書きの閲覧・変更にアクセス制御を適用する。認証は今回の必須範囲とし、管理画面と保存・取得・プレビューの各処理で未認証・未許可のアクセスを拒否する。
- **FR-005**: 未保存・保存中・保存済み・失敗を利用者が区別できる。失敗を成功扱いしない。
- **FR-006**: 保存失敗時は同じ画面で入力を保持し、再試行できる（提案）。
- **FR-007**: 自動保存を第一候補として実現性と運用負担を評価する。難しい場合は理由を提示し、保存ボタンを用意する。保存間隔・併用の判断は設計で行う。
- **FR-008**: 共通品質基準に従い、全操作をキーボードで行え、ラベル・保存状態・エラーが認識できることを含めて評価する。
- **FR-009**: 単日・会場開催、複数日開催、オンライン開催の作成・下書き保存・再編集を必須範囲とする。
- **FR-010**: 各開催形式で非公開の詳細ページプレビューを利用できる。プレビューでは公開を実行しない。

### Key Entities

- **イベント下書き**: 告知の識別、入力内容、保存状態、作成者のアクセス権。入力項目候補はタイトル・開催日・会場・住所・アクセス・日時の案内・料金・補足・主催者。現行表示型からの候補であり、編集項目の確定ではない。
- **映画タグ／イベントタグ**: 告知に関連づける分類。どちらも任意で複数選択できる。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 合意した代表例で作成→保存→再表示→修正→再保存を完遂し、保存対象の全項目が一致する。
- **SC-002**: タグ未選択・複数選択の両方で保存と再編集を完遂する。
- **SC-003**: 保存失敗を再現して、入力保持・失敗表示・再試行成功の3点を確認する。
- **SC-004**: 権限のない利用者が下書きを取得・変更できないこと、保存で公開内容が変わらないことを確認する。
- **SC-005**: WCAG 2.2 A・AAの達成基準ごとに結果と根拠を記録し、未確認を適合としない。監督の操作確認と開発担当者の検証を分けて記録する。

- **SC-006**: 単日・会場開催、複数日開催、オンライン開催の代表例すべてで、作成・保存・再編集・詳細プレビューを確認する。いずれか未確認なら本Issueを完了としない。

## Assumptions

- 管理画面の利用者は監督と開発担当者の2人。個別アカウント・同じ操作権限で開始する。利用許可・解除の方法、ログイン・ログアウト・セッション期限切れ・復旧を認証設計で具体化する。開発担当者専用の操作が必要になった時点で、その操作の制限を設計する。認証方式・保存先・復旧方法は未決定であり、既存案から自動採用しない。
- 再編集に必要な最小限の入口を設ける提案。全件一覧・検索機能は自動的に含めない。
- 他のコンテンツ種別、公開待ち、公開停止、移行、アップロード、決済は本仕様の範囲外。
- 仕様の確認後に共通デザインシステムで画面設計を行い、実装範囲を確認する。
- #397（保存）、#396（スキーマ）、#334（本文編集）との境界は設計段階で照合する。
