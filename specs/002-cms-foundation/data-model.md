# CMS共通の保存・履歴設計

対象: #392 / #396 / #397

## ContentDraft

| 属性 | 意味 |
| --- | --- |
| id | サーバー発行UUID。不変 |
| version | 1から始まる保存世代。条件付き更新に使用 |
| type | 登録済みのコンテンツ種別。最初はevent |
| payloadSchemaVersion | 種別データのスキーマ版 |
| payload | 種別ごとの編集中データ |
| createdAt / updatedAt | サーバーUTC時刻 |
| createdBy / updatedBy | 検証済み認証主体。クライアント指定不可 |
| copiedFromId | 複製元の追跡用参照。同期関係は持たない |

D1にはid主キー、version整数、payload JSON、時刻・操作者を保存する。保存世代は公開revisionと別概念。既存の公開revisionは変更しない。通常保存では UPDATE ... WHERE id = ? AND version = ? として世代を増やし、更新件数0なら競合を返す。

## 複製

保存済みの元データを指定versionで複製する。編集画面に未保存変更がある場合は先に保存し、成功後だけ複製を実行する案。競合なら複製しない。

複製はCMS共通機能とし、種別ごとの入力内容（イベントではタイトル・日時・開催状態・会場・説明・タグなど）をそのままコピーする。今回の対応種別はイベント。新しいid・version・作成日時・操作者を発行し、公開状態・公開日時・番号・URL識別子・revision履歴をコピーしない。

作成・更新・複製には操作IDを付ける。操作IDと認証主体に一意制約を置き、同じ操作ID・同じ内容の再送は同じ結果、異なる内容なら409とする。D1のトランザクション境界で下書きの作成・更新と操作記録を確定する。

## 公開履歴と復元

履歴は公開成功時の内容だけを対象とする。自動保存・「保存」ボタンは最新の下書きを保存し、履歴を作成しない。時間間隔での履歴作成も行わない。公開前の編集途中の版には戻れない。

公開履歴はコンテンツID、公開版の識別子、payloadSchemaVersion、実際に公開したpayload、公開日時、公開した操作者を持つ。公開版の識別子と下書きのversionは別概念とする。同じ公開要求の再送で履歴を重複作成しない。同内容の連続公開でスナップショットを重複させず、公開された事実と対象内容との対応を保持する。

公開失敗を公開済み履歴にしない。公開処理・履歴・保持件数の整合性を確保する具体的な契約は公開機能の設計で確定する。公開処理は今回の段階②の実装対象であり、その先頭で接続契約を具体化する。公開履歴・復元の受け入れには公開機能との接続が必要であり、下書き保存だけで完了とは扱わない。

復元は公開履歴から内容を確認して実行する。現在の下書きversionを照合し、競合時は409。復元直前の下書きを別枠で保護してから、選択した公開内容または保護した下書きを新しい下書きversionへ保存する。保護と下書き更新は原子的に確定し、保護に失敗したら復元しない。復元元の種別と識別子を操作記録に残す。コンテンツID・公開状態・現在公開中の内容は変更しない。対象履歴が同じコンテンツに属することとスキーマの互換性を検証する。

編集画面に未保存入力がある場合は先に保存し、成功してから公開履歴を開く。直前の入力は最新の下書きとして保持し、履歴を開くだけでは保護用データも追加しない。保存失敗時は編集画面に留まり入力を保持する。復元後は返された内容と保存世代でフォームを更新してから自動保存を再開する。

### 履歴の保持

公開履歴はコンテンツごとに現在公開中の版を含めて直近3件保持する。4件目となる新しい公開が成功した時点で、最も古い公開履歴を削除する。公開失敗や同一要求の再送では保持件数を消費しない。期限は設けず、更新の間が空いても日数では削除しない。現在の下書きと現在公開中の内容を削除しない。

復元直前の下書きは公開履歴3件とは別枠で期限なしに保護し、公開履歴の件数整理では削除しない。表示上は同じリストに統合し、保護した下書き1件を「編集中」として先頭に置き、公開履歴を「公開済」として最大3件表示する。編集中は現在の入力内容ではない。共通の選択・復元操作で戻し直す。保護枠は記事ごとに1件とし、復元成功のたびに直前の下書きへ置き換える。古い保護データはその時点で削除される。「期限なし」は時間経過では削除せず、次の復元成功まで保持する意味とする。保護した下書き自体を復元する場合も、置き換え前の保護内容を復元元として確保し、直前の下書きと入れ替える。保護枠の置き換え・下書き更新・操作記録は同一トランザクションで確定し、失敗・競合時は両方の保存内容を変更しない。同一操作IDの再送は元の結果を返し、保護枠を再度置き換えない。記事自体の完全削除に伴う関連データ削除も別途設計する。

公開履歴の件数は記事ごとに上限があるが、全体容量は記事数・各payloadのサイズ・別枠の保護データに依存する。バックアップはDB障害からの復旧用として併用する。

## UIの保存状態

未保存 → 保存中 → 保存済み。失敗時は未保存内容を保持して再試行。保存要求の開始時点の入力世代を記録し、応答後に追加入力があれば保存済みと表示しない。古い応答で新しい入力を上書きしない。

プレビューは表示時のフォームデータを安全な表示モデルへ変換し、保存状態とは独立して表示する。画面切替でフォームを破棄しない。
