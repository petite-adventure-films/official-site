# CMS共通の保存・履歴設計

対象: #392 / #396 / #397

## ContentDraft

| 属性 | 意味 |
| --- | --- |
| id | サーバー発行UUID。不変 |
| version | 1から始まる保存世代。条件付き更新に使用 |
| type | 登録済みのコンテンツ種別。最初はevent |
| payloadSchemaVersion | 種別データのスキーマ版 |
| payload | 種別ごとの編集中データ |
| createdAt / updatedAt | サーバーUTC時刻 |
| createdBy / updatedBy | 検証済み認証主体。クライアント指定不可 |
| copiedFromId | 複製元の追跡用参照。同期関係は持たない |

D1にはid主キー、version整数、payload JSON、時刻・操作者を保存する。保存世代は公開revisionと別概念。既存の公開revisionは変更しない。通常保存では UPDATE ... WHERE id = ? AND version = ? として世代を増やし、更新件数0なら競合を返す。

## 複製

保存済みの元データを指定versionで複製する。編集画面に未保存変更がある場合は先に保存し、成功後だけ複製を実行する案。競合なら複製しない。

複製はCMS共通機能とし、種別ごとの入力内容（イベントではタイトル・日時・開催状態・会場・説明・タグなど）をそのままコピーする。今回の対応種別はイベント。新しいid・version・作成日時・操作者を発行し、公開状態・公開日時・番号・URL識別子・revision履歴をコピーしない。

作成・更新・複製には操作IDを付ける。操作IDと認証主体に一意制約を置き、同じ操作ID・同じ内容の再送は同じ結果、異なる内容なら409とする。D1のトランザクション境界で下書きの作成・更新と操作記録を確定する。

## 保存履歴と復元

今回に含める設計案: 成功した保存の内容をスナップショットとして残し、選んだ履歴を同じコンテンツの新しい下書き版として復元する。差分の再構成・行単位の比較UIは追加しない。

DraftRevisionはdraftId、version、payloadSchemaVersion、payload、savedAt、savedBy、保存種別（作成・自動・手動・復元）、restoredFromVersionを持つ。draftIdとversionを一意にする。現在値の条件付き更新、履歴追加、操作ID記録を原子的に確定し、失敗時は全体を戻す。変更のない保存・同じ操作IDの再送で履歴を増やさない。

復元は履歴一覧から内容を確認して実行する。現在のversionを照合し、競合時は409。選択したpayloadを新しいversionへ保存し、元の履歴と復元前の版を保持する。コンテンツID・公開状態・公開revisionは変更しない。対象履歴が同じコンテンツに属することと現在のスキーマとの互換性を検証する。

編集画面に未保存入力がある場合は先に保存し、成功してから保存履歴を開く。直前の入力は履歴の最新版として存在する。保存に失敗したら編集画面に留まり入力を保持する。復元後の自動保存が古いフォームを送らないよう、進行中の保存を完了させてから復元し、戻った版でフォームと保存世代を更新する。

保存スナップショットを毎回残す方式を第一案とするが、自動保存による容量・履歴一覧の使い勝手を評価して保存単位と保持方針を確定する。保存履歴の自動削除はこの案では導入しない。保持条件を決める前に本番運用を開始しない。バックアップはDB障害からの復旧用、履歴はコンテンツ単位の内容復元用として併用する。

## UIの保存状態

未保存 → 保存中 → 保存済み。失敗時は未保存内容を保持して再試行。保存要求の開始時点の入力世代を記録し、応答後に追加入力があれば保存済みと表示しない。古い応答で新しい入力を上書きしない。

プレビューは表示時のフォームデータを安全な表示モデルへ変換し、保存状態とは独立して表示する。画面切替でフォームを破棄しない。
