## Summary

Cloudflare Accessの2メールアドレス限定認証、CMS専用Worker、D1による保存を使用する構成。保存・複製・履歴・復元は共通処理とし、種別固有の空データ・検証・入力フォーム・一覧要約・プレビューをアプリの組み立て箇所で接続する。

## Technical Context

- Language/Version: TypeScript、Node 24。
- Primary Dependencies: React、Vite、Tailwind、Workers。選定理由は [research.md](research.md)。
- Storage: D1。保存・再送・履歴の原子的更新は [data-model.md](data-model.md)。
- Testing: Vitest、Worker/D1統合テスト、Playwright。cms/の変更を共通E2E判定へ追加する。
- Target Platform: ブラウザとCloudflare Workers。公開サイトとは別アプリ。
- Performance Goals: 保存待ちでも編集・プレビュー可能。自動保存は入力停止1秒後。保存ボタンを併用する。
- Constraints: 2人・同権限、下書きは非公開、管理画面はPCで受け入れ確認。外部設定は導入時に確認する。
- Scale/Scope: イベントを最初の種別とする。使わない種別・拡張機構を先に実装しない。

## Constitution Check

- 技術構成は確認済み。費用・契約条件・バックアップ先・保持条件は本番導入前に確認する。

## Project Structure

```text
cms/
  src/
    app/                     # routes/providers、機能を組み合わせる箇所
    features/
      auth/                  # セッション、ログイン状態
      content/               # 一覧・保存・複製・履歴・復元の業務操作
      events/                # イベントの入力項目と表示
    components/              # 汎用のボタン・入力欄など
    hooks/                   # 種別にも業務にも依存しない共通フック
    lib/                     # APIクライアント等
    config/
    types/
    testing/
  worker/                    # サーバー専用。認証、API、保存、種別検証
  migrations/
  e2e/
packages/content-schema/     # 検証契約
packages/event-presentation/ # 公開側と共有するイベント表示
```

フロントエンドの配置・依存方向は [Bulletproof ReactのProject Structure](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md) を参考基準とする。`app` が各featureと共通部品を組み合わせる。feature間を直接importせず、featureは汎用の共通層を利用する。共通層からfeatureやappをimportしない。各feature内は必要なapi/components/hooks/types等だけを作る。

`features/content` と `features/events` はappで接続する。例えば共通の編集枠へイベントフォームとプレビューを渡す。汎用componentsに業務ロジックを集めない。

Bulletproof Reactはサーバー構成や仕様フォルダーの規則ではない。worker/は実行環境の境界であり、フロントエンド用モジュールからサーバー秘密情報をimportできない構成にする。

## #433 公開履歴・下書き復元の種別対応

状態は仕様・計画のレビュー案。作業ブランチは `codex/issue-433-cms-history-restore`、統合先は `version-4`。

### 現行コードと変更方針

1. `cms/worker/app.ts` はブログの履歴・復元を公開操作と同じ制御で拒否している。ブログの `history` と `restore` を認証済みの共通経路へつなぐ。ブログの公開・公開前確認の制御は #390 で扱う。
2. `cms/worker/routes/history.ts` の閲覧用変換と `cms/worker/services/restore.ts` の復元で、DBから取得した対象記事の種別を使う。サーバーで対象記事を特定し、履歴を記事IDで絞り、履歴の種類とスキーマ版を照合する。既存のイベント公開版から下書きへの変換は引き継ぐ。
3. ブログの保護下書きと復元結果には既存のブログ下書き検証を使う。本文構造・分類ID・画像とPDFの添付参照を下書き保存と同じ規則で検証する。参照先が存在しない場合や添付種別が一致しない場合は拒否する。現在の下書きも保護枠へ入れる前に対象種別のスキーマを確認する。ブログ公開版から下書きへの変換は #390 の公開スキーマを前提とし、検証用の履歴での確認と実際の公開経路からの確認を区別する。
4. 既存のD1による復元・保護枠更新の原子性、`expectedVersion` の競合検出、利用者と `operationId` による再送処理を引き継ぐ。同一操作の再送は確定済みの結果を返し、同じIDで異なる操作が送られた場合は競合として扱う。画面操作は[既存の公開履歴の画面契約](contracts/screens.md)に従う。

### 検証と依存関係

- Worker/D1の統合テストで、認証・権限外、別記事、種別またはスキーマ不一致、不正な分類、欠落または種別違いの添付を検証する。復元拒否・競合時に下書きと保護枠が維持されること、同一操作の再送で版が進まないことを確認する。
- イベントとブログで保存 → 履歴参照 → 復元 → 再編集を検証する。保護下書きからの再復元で保護枠が入れ替わり、復元前後で公開版が同じであることを確認する。
- ブログの実際の公開履歴を使う通し確認は #390 の履歴生成に依存する。種別固有フォームへの接続・実機受け入れは #418〜#421、Astro描画は #394 で扱う。検証用履歴での成功と種別ごとの受け入れ結果を個別に記録する。

### #390 ブログのローカル配信と履歴確認

- ローカル配信アダプターで、検証したブログ候補を固定して配信する。配信確認が成功したときに既存のD1トリガーが公開状態と履歴を同時に確定する。#433 はこの履歴から本文・分類・添付参照を検証し、下書きへ復元する。
- 検証用ページは `/__cms-blog/<slug>/` に生成する。正式なルート直下のURL、既存URLとの照合、添付の公開表示、一覧への接続は #390・#394 の残作業。Cloudflare向けの配信アダプターには接続していない。
- 一時D1とローカル配信ランナーで、新規保存 → 公開 → 配信ページの取得 → 履歴参照 → 下書き復元 → 再編集・保存を確認した。公開要求後の追加編集は保護下書きに残り、公開版は復元・再編集の前後で同じだった。
