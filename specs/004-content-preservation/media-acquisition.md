# 使用中メディアの取得と検証

対象 #337。公開スナップショットから参照される旧画像・PDFをローカルに取得する。R2登録・assetId対応・公開URLへの接続は #339、新規CMSアップロードは #335/#395、旧記事本文の取込は #338。取得結果を正式移行や本番反映と扱わない。

## 入力と境界

`astro/data/wordpress-export.json`と`wordpress-media-inventory.json`を正本入力にする。スナップショットから台帳を再構成し、パス・URL別名・参照元が一致しなければ取得を開始しない。両ファイルとジョブ計画のSHA-256を固定する。

- 使用中5,935パス・6,073 URLを個別に取得する。HTTP/HTTPSの違いを事前に同一実体としない。
- WordPress生成サイズと思われる33パスの元サイズ候補も別の役割で検証する。9候補は既存参照URLと同じで、追加は24 URL、計6,097ジョブ。
- ブログ詳細計画の5,895パス・6,033 URLとは母集団が異なる。本文外の参照と他種別を含む全サイト台帳を使用する。
- 外部サイトのファイル、未参照ライブラリ、非公開資料は取得対象外。削除してよいという意味ではない。旧URL・記事ID・参照フィールドは保つ。
- 元サイズ候補の取得成功は、縮小・切り抜きの一致や代替採用を意味しない。元URLの欠損を上書きしない。

## 実装

`astro/scripts/acquire-wordpress-media.mjs`。Node 24とAstroのSharp、PDF検証用の`pdfinfo`/`pdftoppm`を使用する。

- キャッシュはGit対象外の`.local/issue-337-media/<計画hash>/`。取得器が作るディレクトリは所有者だけがアクセスできる設定にする。実体はSHA-256名で保存し、元URLと参照元をSQLite/結果JSONへ記録する。
- 同時2件、同一の取得開始間隔500ms。既知の自サイトuploadsのみ許可し、各転送先も検査する。リダイレクト5回、1要求60秒、1ファイル20MiB、全体4GiBを上限の初期値にする。各取得前に空き5GiBを要求する。
- 本文を一時ファイルへ逐次保存する。画像は形式・画素数・全デコード、PDFは構造・ページ数・全ページの低解像度描画を検査する。受信hashとディスク再読出しhashを比較し、検証後にblobを確定する。Content-Type/Lengthは実体検査の代用にしない。
- SQLiteのFULL同期トランザクションで取得状態・試行・受信量を記録。要求開始前に1ファイル分の容量枠を予約し、確定した実受信量との差だけ返す。中断した要求の予約枠は返さず保守的に残す。上限超過応答は受け取ったchunkを含む実byte数を記録して拒否するため、転送量はネットワークのchunk境界で上限を超える場合がある。
- 408/429/5xx・通信失敗は最大3試行。Retry-Afterを全体で共有し、30秒超の待機指示では状態を保存して止める。連続失敗も停止する。404/410はmissing、その他の拒否・破損は理由を残す。
- 排他ロックにより同じ保存先の同時実行を拒否する。再開時は入力hashと取得済みファイルのSHA-256/サイズを再照合する。破損・欠落は取得対象に戻し、破損blobは隔離する。Rangeによるバイト途中再開は行わない。
- 結果集計で元URLの欠損、候補、別名のhash不一致を分ける。成功数・URL数・パス数・固有blob数を混同しない。

## 実行と再開

リポジトリ直下で実行する。

```sh
node --test astro/scripts/acquire-wordpress-media.test.mjs
node astro/scripts/acquire-wordpress-media.mjs --limit 70
node astro/scripts/acquire-wordpress-media.mjs
node astro/scripts/acquire-wordpress-media.mjs --offline
node astro/scripts/summarize-wordpress-acquisition.mjs <cache>/result.json <cache>/summary.json
```

`--limit`はこの起動で処理する試行数を制限する。途中のpendingが残る場合の終了コード2は全件成功ではないことを表す。`--offline`は新たなネットワーク取得を行わず、取得済み実体を照合する。missingは取得結果として残るため、終了コード0だけで欠損ゼロと判断せずcounts/summaryを読む。

異常停止で`acquisition.lock`が残った場合は、記録されたPIDと実際のコマンドを確認し、所有プロセスの終了を確認してからそのロックだけを除いて再開する。動作中のロックを外さない。SQLiteやblobは削除しない。中断した`.part`は成功ファイルではなく、再開で参照しない。長期保全・別媒体へのバックアップ・最終同期は別途必要。
