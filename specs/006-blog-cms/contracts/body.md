# 本文の編集・保存契約案

対象 #334・#418、添付 #395、移行 #391、公開表示 #394。利用者から委任された範囲で細部を具体化したレビュー案。Tiptapを編集基盤にし、PAF用ノードを使ったバージョン付きJSONを保存する。以下はアプリへの実装・本番移行済みを意味しない。

## 保存形式

`rich-text/v1` は変更せず、新しい `rich-text/v2` を設ける案とする。Tiptapの全ノード・属性をそのまま許す形式にはしない。保存・公開・履歴復元・プレビューが同じノード定義と検証器を使用する。Tiptap本体のバージョンと本文データのschemaVersionは別に管理する。

| 内容 | v2の契約案 |
| --- | --- |
| 段落・見出し・リスト・引用・改行・罫線 | ノード名と子要素を限定。見出しはh2〜h4を新規入力の候補とし、記事タイトルのh1と分離。移行で範囲外を見つけたら黙って変更しない |
| 基本文字装飾 | bold/italic/underline/strike/link。装飾解除は選択範囲に限る |
| 画像 | assetImage。assetId、記事ごとのalt/caption、表示寸法・配置。元ファイル・派生画像の実URLはassetから解決する |
| 添付へのリンク | 自サイト画像/PDFはassetKind付きassetLink mark。assetIdと表示文字列を保持する。外部PDFは通常linkとして元URLを保持し、自動移管しない |
| 通常リンク | link mark。内部相対URL、http/https/mailto/telの検証済みhref。イベントハンドラー・任意HTML属性を持たせない |
| 動画 | externalVideo。provider（youtube/vimeo）、videoId、検証済みsourceUrl、title、width/height。provider/IDとURLの整合をサーバーで再検査する |
| 旧記事の書式 | 必要な色、fontFamily、fontSize、lang/dir、アンカー、wbrの意味を限定されたノード/属性に対応。汎用style文字列を実行しない |
| 表 | 既存の構造ノードとセル結合・見出しセルを保持する。新規挿入UIは初期ツールバーへ増やさず、必要性と操作確認を別途扱う |

上表を起点に[保存/公開境界と2つの候補schema](body-storage.md)を設け、310件で設計検証した。候補は未登録であり、正式v2のJSON Schemaをアプリへ追加したものではない。画像・PDFはファイルの保全とID対応が完成する前に仮IDへ置き換えない。外部サイトの画像URLはローカルassetと誤認せず、取り込み/保全方法が決まるまで原本側で保持する。

## 原本と未対応記事

取り込み元のHTMLを不変の保全記録（記事ID、source ID、取得時刻、原本hash）へ残し、編集用JSONと分離する。原本の更新や削除を編集保存の副作用にしない。

1. 原本HTMLの要素・属性・参照を先に列挙する。
2. 許可済みノードへの変換を試し、本文文字列だけでなく画像・リンク・動画・アンカー・意味のある書式を照合する。
3. 未対応要素、未解決asset、差分がある記事は「変換確認待ち」にする。変換で落ちたJSONを通常の編集本文として開かない。
4. 確認待ち記事は本文を読み取り専用にし、「旧形式のため、本文の編集準備中です」と表示する。タイトルや分類を保存する場合は、本文の不変参照をそのまま保持する。本文全体を空や部分変換JSONで上書きできないようAPIで拒否する。
5. 変換・表示を確認するまで再公開を許可しない。既存の公開本文は維持する。未対応箇所を削除して先へ進むボタンは設けない。

この移行状態は通常の公開ステータスと分けて管理する。本文の不変参照はサーバー発行・記事に所属するものに限定し、クライアントから別記事の参照やraw HTMLを指定できないようにする。公開側に原本保全APIを提供しない。

## 動画の設計検証

[専用ノードの試作](../verification/video-node-probe.mjs)を旧ブログの動画がある90記事へ適用した。YouTube 149個、Vimeo 2個でprovider/ID/sourceUrl/title/width/heightをHTML→JSON→HTML→JSONで保持した。YouTubeのsi/start、VimeoのhをURLの一部として保持する。Vimeoのhを落とすと視聴できなくなる場合があるため、IDだけを保存する形式にはしない。

ホストはURL構文で解析して完全一致させ、試作はHTTPSの `www.youtube.com/embed/{11文字ID}` と `player.vimeo.com/video/{数字ID}` のみを許す。未知パラメータ・重複パラメータ・不正ID・資格情報付きURL等は確認対象へ戻す。ホスト偽装、javascript、HTTP、ポート変更など12例の拒否を確認した。[結果](../verification/video-node-result.json)。

試作は動画だけの検証で、画像・他の本文を保持する変換器ではない。ブラウザの実再生・許可属性・CSP・通信先は未検証。新規入力の通常の視聴URLや短縮URLは、別途正規化してこの保存形式へ変換する。単なる文字列置換でホストやIDを取り出さない。

## 保存・公開時の検証

- 下書きは空本文・編集中の未完成内容を保存できる。本文が空という理由だけで保存失敗にしない。
- 公開はタイトル・カテゴリに加え、空白以外の文字、表示可能な画像、PDFリンク、動画のいずれかが本文にあることを条件とする案。画像だけ・動画だけの記事を文字数0として拒否しない。
- 不正ノード、未知schema、許可外URL、未所属のassetや原本参照はサーバーで拒否する。クライアント側検証だけを信頼しない。
- 貼り付けは許可する要素・属性への変換を先に行い、削除される本文や埋め込みがある場合は反映前に知らせる。スクリプト等の実行可能内容は受け付けない。画像ファイルは本文へbase64で埋めず、添付処理へ渡す。
- 検索用文字列はtextノード・リンク表示文字列から導出する。HTML属性・動画URL・asset ID・保全原本を検索文字列に混ぜない。下書き更新と同じ処理で更新する。
- 公開用HTMLはサーバーの許可済みレンダラーで生成する。原本HTMLや保存JSONのattrsを無検査でHTMLに展開しない。保存JSONを正本とし、ブラウザ由来のHTMLを正本として二重保存しない。
- 同内容判定の前に属性順・既定値・書式値を正規化する。段落や空白など本文の意味を無断で削らない。正規化仕様をバージョン管理し、旧履歴のhashを後から変更しない。

## 容量

現行の変更APIは要求全体を256KiBで制限する。[現行試作のChromium全件検証](../verification/editor-prototype/all-articles.md)では、通過310件の本文JSONは最大226,122 bytes（記事14975）、旧分類値を使った暫定要求は226,810 bytes。上限まで35,334 bytesの余裕がある。全件が試作の原文照合・往復検証を通過したが、正式形式での保存可能性は別途確認する。正式v2・CMS ID解決後の最終要求は再測定が必要。初期の標準Tiptap構成で測った195,962 bytesとはノード構成が異なる。

[容量の測定結果](../verification/body-size-summary.json)。動画試作の再実行は、互換性検証と同じ隔離依存を用意し、Node 24で `TIPTAP_AUDIT_DEPS=/tmp/paf-tiptap-recheck node specs/006-blog-cms/verification/video-node-probe.mjs` を実行する。動画試作は期待値不一致なら終了コードを非0にする。

当面は共通APIの制限を維持する案とし、超過を切り詰めて保存しない。入力を保持し、保存できない理由を表示する。原本HTML・画像ファイルを本文要求へ同梱しない。正式形式で既存記事を保存できない場合は、上限引き上げを実測と合わせて設計へ戻す。

## 編集操作

通常の本文操作は段落・見出し、太字、箇条書き、番号付き、引用、リンク。挿入は画像、PDF、動画を分ける。「その他」に斜体・下線・取り消し線・罫線・書式解除を置く案とする。色・フォントの新規指定を初期操作へ増やさず、旧記事の必要な書式は保持する。

ツールバーは本文内の選択位置を維持して操作し、選択状態と操作不能状態をMUI部品の状態で示す。日本語変換中のEnterを保存やツールバー操作へ流さない。リンク/添付ダイアログを閉じたら選択位置へ戻す。Undo/Redoは本文編集に限定し、保存・公開履歴の復元とは区別する。本文の変更は既存の自動保存経路に集約する。

Figmaの通常状態は[画面契約](screens.md)に記録。独立試作で入力・Undo・保存・保存失敗・変換確認待ちを検証済み。正式CMSでのフォーカス、空本文、添付挿入、OS IMEを含む操作確認は残る。

### 旧書式の正規化と保全（試作検証済み・正式v2は未実装）

[操作試作](../verification/editor-prototype/README.md#旧書式言語属性の保持)で、対応するtextStyle属性だけをCSS解析で正規化し、paragraphのlangを保持した。原文の属性・書式/リンクの対象の照合と、正規化後のJSON往復安定性を別々に検証する。原文は上書きしない。

文字・画像ごとの有効な書式とリンクを比較し、同じ書式の隣接文字列を統合する。ラッパー順序や同義の分割/入れ子は許容するが、書式や対象の変更は拒否する。brの位置・数を保持し、br自体の文字装飾は比較しない。空白・通常段落境界の完全な意味比較は別途必要。17696/4318の保存・追記・再読込、lang31箇所と添付参照保持を確認。色/書体や適用対象が異なる負例、lang欠落、不正CSS・未対応langの拒否も検証した。正式ノード・全記事移行の受け入れ確認は別途必要。


### 全310件の検証と残件

現行試作をChromiumで全件実行し、310件すべてが原文照合・JSON往復・localStorage書込/読出しを通過。[全件結果](../verification/editor-prototype/all-articles.md)を参照。操作試験は51記事で追記・保存・ページ再読込を確認。画面操作・API保存・公開・正式v2移行の全件確認は含まない。


### 改行候補の試作検証

wbrはwordBreakノードとして位置・個数を保持し、HTML出力もwbrとする。brや改行文字へ変換しない。全件監査で全17記事279箇所を保持し、対象10記事の追記・保存・再読込も確認した。実エディターで広い幅では改行せず、狭い幅では候補位置で折り返すことを確認。欠落・位置変更・強制改行化は署名比較で拒否する。正式v2・公開レンダラー・OS IMEと不可視ノードの編集操作全般は未確認。


### 旧コンテナーと参照の保全（試作）

観測済みのdiv/spanを専用ノードとして保持し、id・lang/dir・class・補助属性を保存する。リンクのhrefと転送用data属性を区別し、元のクリック先を変えない。mailtoは単一ASCIIアドレスのみを許可する。strongに直接付いた色は変換用コピーで独立した書式として保持する。原文は変更しない。

元から重複するID（10297のfbPhotoSnowliftCaption）は試作では順序・個数を保ち、勝手に改名しない。正式v2と公開レンダラーでは、重複ID/旧アンカーの方針、コピー元class/data/tabindex/aria属性の適用・保全の区分を決める必要がある。元の外部CSS/スクリプトは読み込まない。今回の通過を、そのまま再公開の許可にしない。


### 保存・公開境界の候補

[body-storage.md](body-storage.md)で編集本文・不変保全・公開ASTを分離する案を具体化した。旧属性は保全に残し公開ASTへ出さず、未解決添付と重複anchorは公開を止める。候補schemaで310件の保存形式と逆変換を検証。最大の候補本文は148,935 bytes、暫定要求149,338 bytesで、原本/保全情報は別保存となる。正式API・ID解決・公開HTML・履歴接続は未実装。


### 添付URLと実ファイルの照合

[添付解決の契約](asset-resolution.md)で画像src・画像へのhref・PDFを分類した。自サイト参照は既存台帳5,895パスに対応候補があり、外部PDF5箇所は元URLの通常リンクとして保持する。代表画像2点の実体/hash/寸法と欠損候補8URLを確認。全取得・R2登録・実assetId対応は未実施で、公開停止の対象は252記事。
