# CMSデータの保全と復元

対象 #397。CMS内部の正本はD1。本Issueは保全範囲・手順の確定と独立した復元先での読み出し検証を完了範囲とする。稼働先の切り替えや定期運用の導入は含めない。

## 保全範囲

- D1は一部の記事だけでなく、スキーマ、索引、トリガー、適用済みマイグレーションと全テーブルをSQLで保全する。下書き、公開状態・履歴、保護下書き、タグ・分類、URL予約・正規URL、保存・公開・復元操作、media_uploads、hosted_staging_jobsを含む。
- #462で追加した旧ブログ対応表・元データ固定情報も、適用後は全テーブル保全の対象。今回の実環境バックアップは0011までであり、未配備の0012適用済みとは扱わない。
- 画像・PDFはmedia_uploadsの確定assetとoriginal/renditionsの保存キー・サイズ・ハッシュ、および実体を一組で保全する。下書きだけでなく公開履歴・保護下書き・未完了公開操作からの参照も照合する。未使用でも台帳に残る確定実体を、この復元試験で削除しない。
- 確定前のuploads/{id}は未完了台帳と取得時点を記録する。確定済み実体の代わりに一時ファイルだけを保全しない。今回の未確定台帳は0件。一時アップロード中の復元は未検証であり、利用者には再アップロードが必要となり得る。
- hosted_staging_jobsのmanifest_keyが指す生成入力も別ファイルとして保全し、D1の処理記録と対応づける。公開スナップショットだけをCMS正本の代用にしない。生成方式の設計は #413。
- 認証情報は別管理し、SQL・添付・生成入力をGitや公開成果物に含めない。配備設定の再作成は `../002-cms-foundation/contracts/hosted-event-publication.md` を参照する。

## 復元手順

1. 対象環境、取得時刻、適用済みマイグレーションを記録し、更新が入らない時間帯にD1をSQLへ書き出す。ファイルを取得する間に変更された場合は再取得する。取得物はアクセス制限した保存先へ置き、SHA-256を記録する。
2. 全assetの実体と生成入力を保存キーに対応づけて取得する。D1内のサイズ・ハッシュと実体を照合する。元台帳・SQL・ファイル一覧を同じ保全単位にまとめる。
3. 稼働中のDBと独立した空の復元先へSQLを読み込む。全テーブルの全行とスキーマ・索引・トリガーを元の保全データと比較し、integrity_checkとforeign_key_checkを実行する。
4. 添付を別の保存場所へ元のキーで復元し、再読込したサイズ・SHA-256を比較する。各下書き・履歴・保護下書きのJSONを読み、assetIdから台帳・実体まで参照が成立することを確かめる。
5. 生成入力も処理台帳のキーで復元する。復元先にWorker、公開URL、Deploy Hookを接続せず、自動再送もしない。未完了公開操作は配備済み状態と照合してから個別に再開を判断する。稼働先の切り替えは #389。

## 責任分界と未確認

- #395（子 #335）は添付の登録・選択・参照・削除管理を担当。参照中の下書き・公開履歴・保護下書きの実体を失わず、稼働先の削除を独立バックアップへ即時伝播させない。本Issueで削除機能は実装しない。
- #391（子 #337・#339）は旧サイトの必要ファイル取得・正式移行・欠損対応を担当。旧サイトURLや外部動画の存在確認を、CMSの4実体の復元成功に含めない。
- #394は配備先での公開表示、#445は監督操作の確認を担当。本試験は保存データの復元・読み出しであり、復元DBへCMS画面を接続した操作試験ではない。
- 履歴を含む現行全データのリモートD1/R2への復元、未完了アップロード・配信途中からの再開、全R2バケットの網羅保全は未実施。リモートD1試験とローカル全データ復元を区別する。
- 定期バックアップ、失敗通知、別媒体へのコピー、保存先・保持期間は未決定。今回の手動復元成功を継続運用の完成とはしない。過去のR2・B2・外付けSSD・月次メール案を採用済みと扱わない。
