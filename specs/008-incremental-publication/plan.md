# 公開時の部分生成・配備設計

対象 #413。2026-11-22、`codex/issue-413-publication-design`、統合先version-4。設計レビュー案。[仕様](spec.md)の一覧方針は合意済み。本書の生成・成果物保持・失敗処理は確認待ちで、公開経路へまだ導入しない。

## 概要

通常の記事公開では、確定済み公開データと新候補の差から必要なHTMLだけをAstroで生成する。変更のない成果物を前の公開版から保持して、全パスを含む新しい配備候補を作る。全件生成してから差分だけ送る方式とは分ける。

現行のCMS公開要求・履歴・直列化・配備版照合を利用し、`prepare-staging-release.mjs`の全件生成部分を差し替える。通常公開を部分生成にする実装は#336、一覧・URL・生成対象の表示整合は#394、公開停止・失敗復旧・運用は#390。#413にそれらの実装完了を重ねない。

## 技術条件

- Node 24、現在のAstro 7.4.13、既存React/Tailwind/Sharp。新しい描画基盤を導入しない。
- D1の確定公開版から固定候補を作り、生成中の下書き変更を混ぜない。
- 不変な公開入力、全成果物、パス/hash台帳を、認証付きの保全先へrelease ID単位で保存する。保存先の接続は既存R2・#397の保全方針を利用する。CloudflareのWorker版だけをバックアップにしない。
- `setPrerenderer`で対象だけをrenderする。既定prerendererのsetup/render/teardownと画像metadataを維持する。Viteのバンドル、ルート候補の列挙、全入力の読み取りは残るので、レンダリング削減と別に測る。
- 成否条件は速度の推測値ではなく、対象外詳細のrender 0件、保持HTMLのhash一致、全件生成との出力一致。時間・取得量・生成数・転送量は別々に記録する。

## 生成対象の決定

全ルートについて、HTMLを描画する前に「表示に使う値」を計算してhash化する。旧版と新版のルート集合・入力hashを比較し、追加/変更/削除/保持を決める。記事IDだけの依存関係や、本文だけのhashでは決めない。

| 変更 | 判定へ含める値と対象 |
| --- | --- |
| 新規公開 | 新詳細、所属年/分類/タグ/おすすめ/WS報告の一覧、先頭枠。一覧に入らなくなった記事も含めて並びを比較 |
| 本文更新 | 詳細。お知らせは本文を持つ年別一覧・新着一覧、最新1件ならトップも対象。概要を使う一覧は概要の値を比較 |
| タイトル | 詳細と、タイトルを出す所属一覧・関連表示。関係のない詳細は保持 |
| 日付変更 | 変更前後の年、ソート順、新着の境界、件数、構造化データ。CMS管理日時と旧公開日を区別 |
| 分類/タグ/おすすめ/WS変更 | 変更前後の所属一覧、表示タグ、WSトップの新着5件。現在ない「関連記事」や検索ページを新設しない |
| slug変更 | 新詳細、参照リンクを持つページ、旧URL転送、完全URL集合からのsitemap。旧URLの所有権・循環・予約ルートを検査 |
| 公開停止 | 対象詳細を削除し、一覧/件数/リンク/転送を再評価。停止URLを古いHTMLのまま残さない。旧URLを別記事へ自動転送しない |
| 添付の変更 | 本文と表示資産参照。配信可能性の確認は#395/#339の契約を要求し、未確定assetは候補に入れない |

### 既存実装で見つかった依存

- `/`はお知らせ最新1件の本文を表示する。本文更新もトップへ影響し得る。
- `/workshop/`はWS報告の最新5件。WS所属と並び順を含む。
- メディア掲載・チャンネルの一覧は現在全件表示。年度分割へ勝手に変更せず、対象一覧1ページを再生成する。
- CMSイベントの表示番号は全公開集合から算出される。公開停止や過去日付の追加で別記事の番号が変われば、その詳細・一覧も対象。番号を固定IDへ変更する判断はこの設計に含めない。
- イベントの新着判定と年別リンクには現在日時の依存がある。生成用のJST日付を候補に固定し、日付・年の切替も依存変更として扱う。必要な定時更新は#390で運用へ接続する。
- 現在の公開サイトには独立した全文検索用データ生成がない。存在しない検索成果物を条件に追加しない。将来追加するならルート台帳へ依存を登録する。

## 成果物と配備

1. 公開要求を取得し、直前release・コード・依存lock・設定・入力形式の識別子を固定する。
2. 直前の全成果物と台帳を読み、全パス/hashを検証する。通常公開で元成果物が失われたら停止する。復旧用全件生成を通常公開成功へ偽装しない。
3. 対象HTMLだけを別ディレクトリへ生成する。生成ログと対象集合の一致を検査する。
4. 直前の完全成果物へ、削除・置換・新規HTML・必要資産を反映する。部分生成ディレクトリを丸ごと上書きしない。部分sitemapや404・robots・公開外画面を誤って置き換えない。
5. sitemapは公開候補全体のURL集合から再生成し、既存の除外方針を維持する。redirectsは全規則を生成し、二重定義/循環/公開停止先を検査する。
6. 全成果物manifestを確定・保全し、候補をuploadする。未変更パスもmanifestへ含める。配備markerには入力hashと、marker自身を除いた内容manifestのhashを含める。hashの自己参照を避け、markerを含む完全配信manifestは別途保全する。
7. 活性化直前に直前releaseが変わっていないことと、既存の公開処理の所有権を再確認する。version IDを100%へ切り替え、配備ID・marker・必要ページ/資産を照合してCMS公開版を確定する。

既存`run-hosted-staging.mjs`と公開担当Workerのclaim/activate/verify/succeedを保つ。Workerの切替は全拠点・HTML/資産の一括原子性を保証しない。固定時間の待機や一地点のmarker一致を全世界の一致と扱わない。[公式のversion skew説明](https://developers.cloudflare.com/workers/versions-and-deployments/version-skew/)を踏まえ、資産互換を独立したゲートにする。

### 資産互換のゲート

同じURLの内容を変更しない。候補が参照する旧資産は保持し、新しい画像・PDF・コード資産を導入する場合は旧HTML/新版資産と新HTML/旧配備版の両方向を検査する。新manifestへ旧資産を残すだけでは後者を防げない。

#395/#339は画像・PDF、#336/#390はCSS・JavaScript等のコード資産について、版に依存しない不変資産URL、または同等の互換性を保証する方法を実装・確認する。該当するゲートを満たすまで、新資産を伴う候補は公開しない。単なる全件生成への切替ではversion skewは解消しない。未公開添付の先行公開やR2の公開設定を、本設計の承認だけで許可したとは扱わない。通常の既存資産のみの更新と、新資産導入の受け入れを区別する。

## 失敗・同時更新

| 状態 | 動作 |
| --- | --- |
| 入力/基準版/資産検証、生成、upload失敗 | 現行配信とCMS確定版を維持。候補とエラーを保持し、同じ要求で再試行 |
| 活性化直前に基準版が変わった | 古い差分を適用せず、新しい確定版から候補を再作成 |
| 活性化後に応答紛失・確認失敗 | unknownのまま直列化を維持し、版IDとmarkerを照会。同じ要求で別版を無条件作成・再配備しない |
| 部分更新の後に戻す | 保存済み完全成果物と入力から既存復旧経路を使用。入力JSONだけを戻さない |
| slug/公開停止の再試行 | 同じoperation ID・候補hashへ戻し、旧URL削除/転送を重ねて別結果にしない |

共通レイアウト、CSS/JS、依存lock、Astro、ルート規則、描画schema、共通データ解釈の変更、年別一覧への初回切替、初回導入・成果物復旧は全件生成を明示する。対象不明のときに無言で部分公開しない。

## 原則・品質確認

原文・URL・未採用候補を保持し、承認なしに一覧構成を追加変更しない。静的な年別導線でJSなし・キーボード・直接リンク・戻る操作を確認する。共通デザイン定義の利用は#394で実画面と合わせて確認し、この文書だけでFigma/UI承認済みとしない。保全先と失敗時の復旧を定義し、下書きを公開対象に含めない。設計後も上記のゲートを維持する。
