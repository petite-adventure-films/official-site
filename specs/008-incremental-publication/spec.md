# 公開時に更新するページと一覧の構成

対象 #413。設計案。合意後に #390・#336・#394 の実装範囲に反映する。

## 現状と今回の測定

ローカルの `cms-events/v1` フィクスチャで、イベント1件のタイトルだけを変更してAstroを2回ビルドした。各回735ページを生成し、HTMLのハッシュが変わったのはイベント詳細と `/events/` の2ページ。残り733ページのHTMLが一致した。この結果はタイトルの変更例であり、日付、タグ、slug、新着追加、公開停止で影響する経路は別に検証する。

## 一覧の選択肢

| 選択肢 | 更新時の範囲と閲覧上の影響 |
| --- | --- |
| 番号付き一覧を維持 | URL・ページ移動が分かりやすい。先頭追加や公開停止で後続ページの内容がずれ、一覧部分の再生成が広がる |
| 期間ごとに分けた静的一覧 | 該当する期間と新着欄を更新する。過去の一覧は期間への直接リンクでたどれる。旧ページ番号のURLの扱いと、期間内で件数が多い場合の見せ方を決める必要がある |
| 「もっと見る」などの追加取得 | 一覧データと表示を分けやすい。JSなしでも過去記事へ到達できるリンク、戻る操作、直接リンク、検索エンジン向けの発見経路を設計する必要がある |

**提案**。イベントは既存の年別アーカイブを活用し、最新の一覧と影響した年のページを更新する。ブログは、既存の記事URLを維持しつつ、一覧を年など安定した区切りで扱う方式を第一候補にする。旧一覧URLの対応と閲覧導線を確認してから、ブログのページ番号の扱いを決める。

## 記事変更の影響範囲

| 操作 | 生成・更新する候補 |
| --- | --- |
| 作成・公開、公開停止 | 該当詳細、所属する期間・カテゴリ・タグの一覧、最新枠、関連表示、件数・検索用データ・サイトマップの該当部分 |
| 本文のみ変更 | 該当詳細。概要・検索・関連記事に本文を使う場合は、その参照先も更新 |
| タイトル・日付・カテゴリ・タグ変更 | 該当詳細と対象項目を表示する一覧。所属先が変わる場合は変更前と変更後の両方。関連表示・件数・検索用データも参照に応じて更新 |
| slug変更 | 新詳細、旧URLからの転送、記事を参照する一覧・関連表示・サイトマップ。固定ページや予約済みURLとの衝突を止める |

## 生成・配備の提案

公開確定版と候補から対象ルートを決め、対象だけを既存のAstroテンプレートと同じ表現で生成する。現行Astroで対象ルートだけ生成する入口の実現性は未検証。検証では生成時に通ったルートを記録し、全ビルド後にファイルを選ぶ方法と区別する。

直前の公開成果物を保持し、再生成・削除・転送が必要なルートだけを新しい配備候補へ反映する。Cloudflare Workers Static AssetsはWorker版ごとにパスとファイルを結ぶマニフェストを持つ。直前の成果物を再利用した完全な候補を検証し、成功後に配備版を切り替える。資産転送の差分化は、ページ生成範囲とは別に測定する。[Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/)・[バージョン切り替え時の資産](https://developers.cloudflare.com/workers/versions-and-deployments/version-skew/)。

公開操作は同じ確定版を基準に直列化する。生成失敗時は現行版を維持し、応答が失われた場合は先に配備版を照合してから同じ要求を再試行する。スナップショットの公開状態は配備結果の確認後に確定する。共通レイアウトやルーティングの変更など、影響が全体に及ぶコード変更は全件生成の対象とする。

## 合意・検証項目

- まずイベントの年別一覧を使う方針と、ブログ一覧の期間構成・旧一覧URLへの対応を確認する。
- 記事1件の公開と更新を行い、生成対象ログに無関係な詳細がなく、配備候補にもその詳細の同一ハッシュが残ることを確認する。既存URL、非JSでの過去記事への到達、戻る操作、一覧のリンクとサイトマップも照合する。
- 生成失敗、公開途中の応答喪失、slug変更と公開停止、同時更新での再試行・配備版の整合を確認する。対象生成入口と版切り替えの実現性を検証環境で確認してから後続Issueを更新する。
