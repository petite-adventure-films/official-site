# 公開時に更新するページと一覧の構成

対象 #413。設計レビュー案。一覧・旧番号URLの転送方針は合意済み。生成・配備方式は[設計](plan.md)で具体化し、確認後に #390・#336・#394 の実装条件へ引き継ぐ。本書の承認は本番設定の変更を許可するものではない。

## 現状と今回の測定

ローカルの `cms-events/v1` フィクスチャで、イベント1件のタイトルだけを変更してAstroを2回ビルドした。各回735ページを生成し、HTMLのハッシュが変わったのはイベント詳細と `/events/` の2ページ。残り733ページのHTMLが一致した。この結果はタイトルの変更例であり、日付、タグ、slug、新着追加、公開停止で影響する経路は別に検証する。

## 一覧の選択肢

| 選択肢 | 更新時の範囲と閲覧上の影響 |
| --- | --- |
| 番号付き一覧を維持 | URL・ページ移動が分かりやすい。先頭追加や公開停止で後続ページの内容がずれ、一覧部分の再生成が広がる |
| 期間ごとに分けた静的一覧 | 該当する期間と新着欄を更新する。過去の一覧は期間への直接リンクでたどれる。旧ページ番号のURLの扱いと、期間内で件数が多い場合の見せ方を決める必要がある |
| 「もっと見る」などの追加取得 | 一覧データと表示を分けやすい。JSなしでも過去記事へ到達できるリンク、戻る操作、直接リンク、検索エンジン向けの発見経路を設計する必要がある |

**合意した一覧方針**。イベントは既存の年別アーカイブを活用し、ブログとお知らせは番号付きページャーを終了して静的な年別アーカイブにする。イベントの `/events/` と `/events/archive/{year}/` を手本に、ブログ・お知らせも既存の一覧トップに新着と年別リンクを置き、`/blog/archive/{year}/`・`/news/archive/{year}/` で対象年の記事を表示する。年別ページからも他の年へ移動できる。ブログ本文は既存・新規とも `/{slug}/`。お知らせは現行コードで一覧内に本文を表示している。既存の個別URLが台帳・外部参照で確認できた場合は維持し、現行の一覧内にある記事も年別アーカイブで読めるようにする。

## 旧一覧URLの転送

- 公開URL台帳からブログ全体・カテゴリ・おすすめ・ワークショップ報告と、お知らせの旧ページ番号付きURLを確認する。
- ページ番号にかかわらず、対応する既存一覧トップへ恒久転送する。例として、`/blog/page/5/` は `/blog/`、`/news/page/5/` は `/news/`、`/blog/recommended/page/2/` は `/blog/recommended/`。カテゴリ・ワークショップ報告もそれぞれの一覧トップへ転送する。
- 本文の既存URLは同じ内容を返す。転送元は予約し、新規slugや新設ルートとの衝突を検出する。Cloudflareで可能な限り一段のHTTP 301とし、サイト内リンクとサイトマップは現行URLへ更新する。
- 台帳の全転送元について、HTTP 301、想定した転送先のHTTP 200、対応する分類の一覧と、そこから過去の年へたどれることを確認する。循環、複数段の転送、404、別分類への誤転送を検出したら切り替え前に直す。転送ルールと対象URLは #391 で整理し、#394・#389 で配信前後に照合する。

## 記事変更の影響範囲

| 操作 | 生成・更新する候補 |
| --- | --- |
| 作成・公開、公開停止 | 該当詳細、所属する期間・カテゴリ・タグの一覧、最新枠、関連表示、件数・検索用データ・サイトマップの該当部分 |
| 本文のみ変更 | 該当詳細。概要・検索・関連記事に本文を使う場合は、その参照先も更新 |
| タイトル・日付・カテゴリ・タグ変更 | 該当詳細と対象項目を表示する一覧。所属先が変わる場合は変更前と変更後の両方。関連表示・件数・検索用データも参照に応じて更新 |
| slug変更 | 新詳細、旧URLからの転送、記事を参照する一覧・関連表示・サイトマップ。固定ページや予約済みURLとの衝突を止める |

## 生成・配備の提案

公開確定版と候補から対象ルートを決め、対象だけを既存のAstroテンプレートと同じ表現で生成する。Astroの `astro:build:start` の `setPrerenderer` を使い、全ルート候補を列挙した後、選択したパスだけをレンダリングするローカル試作を確認済み。生成時に通ったルートを記録する。[Astro Integration API](https://docs.astro.build/en/reference/integrations-reference/#setprerenderer-option)。

直前の公開成果物を保持し、再生成・削除・転送が必要なルートだけを新しい配備候補へ反映する。Cloudflare Workers Static AssetsはWorker版ごとにパスとファイルを結ぶマニフェストを持つ。直前の成果物を再利用した完全な候補を検証し、成功後に配備版を切り替える。資産転送の差分化は、ページ生成範囲とは別に測定する。[Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/)・[バージョン切り替え時の資産](https://developers.cloudflare.com/workers/versions-and-deployments/version-skew/)。

公開操作は同じ確定版を基準に直列化する。生成失敗時は現行版を維持し、応答が失われた場合は先に配備版を照合してから同じ要求を再試行する。スナップショットの公開状態は配備結果の確認後に確定する。共通レイアウトやルーティングの変更など、影響が全体に及ぶコード変更は全件生成の対象とする。

## 対象ルートだけを生成する試作（2026-11-15）

イベントのタイトル変更例で、一時設定の `getStaticPaths` が候補736件から `/events/` と `/events/cms-sample-screening/` だけを返した。レンダリングの呼び出しも2件、出力HTMLも2件。直前のHTML733件を維持して2件を重ねると、更新後の全件ビルドの735件とファイルパス・SHA-256がすべて一致した。

この試作ではViteのバンドルとルート候補の列挙は引き続き実行する。部分ビルドは画像資産やサイトマップも出力するため、ディレクトリ全体を重ねない。タイトル変更時の全件ビルドではHTML2件以外の成果物に差分がなかった。配備候補には対象HTMLと必要な依存資産だけを反映し、URL集合が変わるときは完全な公開URL集合を基にサイトマップを更新する。対象の自動判定、slug変更・公開停止、Cloudflareへの配備・照合は後続の検証。

## 現在の検証（2026-11-22）

現在のAstro 7.4.13で、タイトル変更・新規追加・slug変更・公開停止の4操作を再検証した。各2ページだけをrenderし、旧HTMLとの合成が全件生成とパス/hash一致。公開停止では残るイベントの表示番号も変わり、その詳細を対象へ含める必要があった。[結果](verification/selected-render-result.json)・[再実行方法](quickstart.md)。
